# 02 项目类型适配层(Project-Type Adaptation)

> 版本:v1.0 | 最后更新:2026-09-07 | 配套:[01-AI-PRODUCT-DEVELOPMENT-SOP.md](01-AI-PRODUCT-DEVELOPMENT-SOP.md)

**定位**:核心流程(01 文档的 4 Phase × 17 Stage)**对任何项目保持不变**;本文档定义 5 种项目类型各自在哪些 Stage 注入什么内容。使用方式:新项目启动时先判断类型(可组合),再按本文档的注入点表给 01 的流程加料。

**注意**:本文档的 5 种类型内容**不来自 CareerOS**(CareerOS 是单一 ToC 型产品,无法提供多类型证据),而是按用户需求设计的适配框架;注入点与 01 的 Stage 结构对齐,标注 ⚠ 的条目待未来项目验证(见各类型末)。

---

## 一、适配机制:注入点模型

- **核心不变**:Stage 01–17 的顺序、每个 Stage 的目标与验收模板不变。
- **适配 = 注入**:类型特有内容在指定 Stage 的「核心工作 / 输出物 / 验收标准」中**增加条目**,不替换、不重排。
- **注入点表格式**:`Stage 编号 | 注入什么 | 产出在哪里`。
- **组合**:多类型叠加时(如 ToB + Agent),注入点取并集;冲突时见第八节。

## 二、类型总览

| 类型 | 一句话特征 | 典型产品 | 最重的注入阶段 |
| --- | --- | --- | --- |
| ToB | 卖组织,决策链长,权限与审计是底线 | 企业知识库、营销自动化、HR 系统 | 04 PRD / 05 架构 / 07 技术设计 |
| ToC | 卖个人,留存增长,情绪与信任 | CareerOS 这类个人 AI 助手、内容工具 | 02 用户 / 11 纵向链路 / 14 打磨 |
| ToG | 卖合规,流程与可追溯高于体验 | 政务办事、监管辅助 | 04 PRD / 07 技术设计 / 16 部署 |
| AI 工具型 | 卖结果,输入→处理→输出→编辑循环 | 简历优化、翻译、代码生成 | 06 Agent 设计 / 11 纵向链路 |
| Agent 型 | 卖自主性,规划执行+人工接管 | 自动化 Agent、客服 Agent | 06 Agent 设计 / 13 集成联动 / 04 验收 L5 |

## 三、ToB AI 产品

**核心特征**:使用方 ≠ 付费方(决策链);多角色权限;组织架构与数据权限;审批流;审计合规。

**注入点**:

| Stage | 注入内容 |
| --- | --- |
| 02 用户与场景 | persona 覆盖**购买者/决策者/使用者**三类,分别写痛点(三者痛点不同) |
| 04 PRD | FR 增加:角色权限矩阵、审批流、审计日志、数据导出(合规刚需);NFR 增加:可用性 SLA、数据隔离 |
| 05 产品架构 | 增加:组织架构模型(租户→部门→用户)、权限模型(RBAC/ABAC)、审批流引擎位置 |
| 06 AI/Agent 设计 | 每个 Agent 增加:数据权限边界(只能看到授权范围)、审计落点(输入输出留痕);**Agent 建议 → 人审批** 是默认模式而非例外 |
| 07 技术设计 | 增加:多租户隔离方案(库/Schema/行级)、SSO/企业认证、审计日志存储、数据留存策略 |
| 11 纵向核心链路 | 链路终点延伸为「使用者提交 → 审批人通过」,审批流进 P0 |
| 16 部署 | 增加:企业数据合规(等保/GDPR 视域)、审计日志保留周期、备份策略 ⚠ |

**特有验收项**:

- 越权访问测试(A 租户访问 B 租户数据必须 401/403)——04 文档 L2 层「越权」用例升级为验收重点
- 审批流断点演练(审批人离职/转岗场景)⚠
- 审计日志完整性抽查(每条 AI 输入输出可追溯)

**决策提醒**:ToB 的「明确不做清单」要额外覆盖「不做哪些企业功能」(如不做自定义审批流编排),否则采购方会无限提需求。

## 四、ToC AI 产品

**核心特征**:卖个人价值;体验与情绪直接决定留存;增长靠产品自传播;门槛必须低。

**注入点**:

| Stage | 注入内容 |
| --- | --- |
| 02 用户与场景 | persona 增加:高频场景(每周多少次)、触发情绪(焦虑/期待)、放弃原因假设 |
| 03 竞品与市场 | 增加:获客渠道与替代方案盘点(用户现在怎么解决) |
| 04 PRD | FR 增加:首次价值时刻(TTFV)路径、分享/邀请机制(可选)、隐私控制;NFR 增加:首屏加载、移动端适配 |
| 06 AI/Agent 设计 | 增加:AI 回应的话术温度(情绪价值)、失败时的降级话术(不冷场) |
| 08 设计系统 | 增加:情感化细节(空态文案、加载动效),但受 DesignRules 约束防过度 |
| 11 纵向核心链路 | 验收标准增加:**首次价值时刻 ≤ 5 分钟**(新用户从注册到获得第一个结果);CareerOS 的 Phase 1 验收即此模式 |
| 14 打磨与收敛 | 增加:用户情绪走查(每步操作后的心理状态),不只查视觉 ⚠ |

**特有验收项**:

- 新用户冷启动路径计时(≤ 5 分钟达成首个价值)
- 断网/慢网下 AI 请求的降级体验(不白屏不丢数据)
- 移动端走查(CareerOS 用 375px 横向溢出检查,ToC 是必查项)

**决策提醒**:ToC 的「明确不做清单」要额外覆盖「不做哪些增长功能」(分享裂变/积分/签到等是 Optional,不是 P0)——CareerOS 的分享卡属于后置增强。

## 五、ToG / 政务类 AI 产品

**核心特征**:合规是底线;流程与留痕比体验重要;多角色协同(经办/审核/领导);稳定性压倒一切。

**注入点**:

| Stage | 注入内容 |
| --- | --- | --- |
| 04 PRD | FR 增加:审批留痕、回退机制、角色权限(经办/审核/批准);明确不做清单必须含「AI 自动决策边界」 |
| 06 AI/Agent 设计 | **铁律:AI 只出建议,不出结论**——所有落库动作经人工确认;每条建议附依据与来源 |
| 07 技术设计 | 增加:数据安全(加密落盘/传输)、国产化适配、审计日志;选型对比增加合规维度 |
| 09 实施计划 | 里程碑增加:合规评审点(在每个外发/上线节点前)⚠ |
| 16 部署 | 增加:安全等级保护测评、应急演练、灰度发布;部署时机大概率由上级拍板而非项目组 ⚠ |

**特有验收项**:

- AI 输出可追溯(每条结论 → 依据 → 来源文档)
- 权限矩阵越权测试(与 ToB 相同但更严)
- 长时间稳定性测试(7×24 运行、断点续跑)⚠

**决策提醒**:ToG 的「AI 建议 vs 自动执行」判据(01 文档第七节第 3 条)从默认「可逆可自动」收紧为「一律建议」——这是唯一改变核心判据默认值的类型。

## 六、AI 工具型产品

**核心特征**:卖结果不卖陪伴;核心循环 = 输入 → AI 处理 → 输出 → 编辑 → 反馈 → 再生成 → 导出;用户控制权是体验核心。

**注入点**:

| Stage | 注入内容 |
| --- | --- | --- |
| 05 产品架构 | 核心数据源 = 用户的输入文档/数据;架构围绕「输入 → 结果」闭环设计 |
| 06 AI/Agent 设计 | 增加:结果可编辑性(用户改一个字 AI 要能响应)、再生成入口、结果置信度提示;**逐条接受/拒绝模式**(CareerOS 简历逐条采纳即此模式) |
| 11 纵向核心链路 | 链路 = 完整闭环:上传 → 解析 → 生成 → 对比 → 编辑 → 导出;验收标准 = 从输入到导出全程无阻塞 |
| 12 横向功能扩展 | 文件解析类功能(上传/导出)留返工预算——CareerOS 简历模块的证据(计划 7 任务实际 17)⚠ |
| 15 交付与演示 | demo-flow 必须覆盖「导出结果」这一步(用户掏钱买的是结果) |

**特有验收项**:

- 真实文件解析正确率(用真实文件夹具,不是构造样例)——CareerOS 用中文 PDF/DOCX 夹具
- 导出结果与界面所见一致(所见即所得)
- 再生成幂等性(同一输入两次生成结果可复现或差异可控)

**决策提醒**:工具型的「用规则还是 AI」判定最容易出错——格式、排版、排序一律规则,语义理解才用 AI(CareerOS 的「节顺序保真」用规则不用模型)。

## 七、Agent 型产品

**核心特征**:卖自主性;Agent 自己规划执行多步任务;人工接管与失败处理是生死线。

**注入点**:

| Stage | 注入内容 |
| --- | --- | --- |
| 05 产品架构 | 增加:任务状态机(排队/执行/等待输入/失败/完成)、中断恢复模型 |
| 06 AI/Agent 设计 | 增加:Workflow(步骤编排)、Planning(任务分解)、Tool Calling(工具契约)、Memory(记忆策略)、Context 预算管理、**Human-in-the-loop 触发条件清单**(哪些步骤必须停下来问)、失败重试策略、可观测性(每次调用留痕) |
| 07 技术设计 | 增加:任务持久化与断点续跑、并发任务互斥(防重复执行)、成本控制(每任务 token 预算) |
| 09 实施计划 | 里程碑增加:Agent 评测基准(eval set)建立 ⚠ |
| 13 集成与联动 | 升级为**核心阶段**:Agent 与各工具/数据源的联动是主体功能,不是收尾 |
| 16 部署 | 增加:运行观测面板(任务成功率/耗时/成本)、告警 |

**特有验收项**:

- 任务状态机全路径测试(含「卡死 → 恢复」)——CareerOS 的 stale 判死与轮询修复(`0b04757`、`4834aa3`)证明这类问题必现,必须预先测
- 失败重试不产生副作用(不重复落库/不重复扣费)
- 人工接管后 Agent 状态正确恢复 ⚠
- eval set 回归(与 04 文档 L5 样例集同源,规模更大)

**决策提醒**:Agent 型产品中,「AI 可自主执行的条件」(01 文档 6.5 三同时)需要额外加一条:**涉及外部动作(发消息/下单/改生产数据)一律先确认**。

## 八、类型组合规则

1. **取并集注入**:ToB + Agent 型 = 两组注入点全部启用;ToC + AI 工具型同理。
2. **冲突按安全侧取更严**:ToG 的「AI 只出建议」覆盖 Agent 型的「可逆动作可自主」;ToB 的多租户验收覆盖 ToC 的体验验收优先级。
3. **主类型定节奏**:混合类型项目以「谁决定付费/立项」为主类型确定里程碑节奏(ToB 主 = 审批节点;ToC 主 = 留存指标)。
4. **最多叠加两类主类型**:叠加三类以上的项目,先砍范围再启动——复杂度不是线性增长。

## 九、边界提醒

- 本文档 5 种类型覆盖主流形态,**不为完整而新增分类**;遇到新形态先按最接近的类型启动,复盘时(Stage 17)再决定是否抽象新类型。
- 标注 ⚠ 的条目无法从 CareerOS 验证(单一 ToC 样本),属于「设计上合理、待未来项目验证」——使用时应视为假设而非定论,验证后回流更新本文档。
- 适配层永远不改核心流程的顺序——如果发现某类型需要重排 Stage,优先怀疑是类型判断错了或范围没砍够,而不是核心流程错了。
