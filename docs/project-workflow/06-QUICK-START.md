# 06 快速启动(Quick Start)

> 版本:v1.0 | 最后更新:2026-09-07 | 配套:[01-AI-PRODUCT-DEVELOPMENT-SOP.md](01-AI-PRODUCT-DEVELOPMENT-SOP.md)

**定位**:新项目的执行清单。不需要读完整 SOP,按本文件的 Step 顺序走;卡在某一步时,再打开对应文档深读(每步都标注了去处)。

**节奏预期**(CareerOS 实测参考,非标准):文档阶段(Step 1–7)约 1–2 天;编码主功能(Step 8)约 7 天(138 提交中的 115 个);打磨与交付(Step 9)约 4 天。单人 + AI Coding 的节奏。

---

## Step 0 创建项目骨架(10 分钟)

- **做什么**:按 [05-PROJECT-TEMPLATE.md](05-PROJECT-TEMPLATE.md) 第一节建目录 + 写 CLAUDE.md(用第四节模板全文)。
- **输出**:目录 + CLAUDE.md。
- **AI 干什么**:全部代劳(创建目录、生成 CLAUDE.md)。
- **人干什么**:确认 CLAUDE.md 的 git 规则符合预期(自动 commit/push 是否接受)。
- **怎么算完成**:`ls` 可见目录;CLAUDE.md 含 git 纪律与环境纪律。

## Step 1 定义产品(约 1 小时)

- **做什么**:回答四问——为谁、解决什么问题、为什么是现在、成功长什么样(可度量)。
- **输出**:memory-bank/product-vision.md。
- **AI 干什么**:访谈式提问 + 起草;人回答。
- **人干什么**:拍板定位、边界(明确不做什么)、成功标准。**这一步 AI 不能替你决定。**
- **怎么算完成**:四要素齐全,人对边界无异议。
- **深读**:01 文档 Stage 01。

## Step 2 定义用户(约 1 小时)

- **做什么**:写 1–3 个 persona(场景 + 痛点 + 当前替代方案)。
- **输出**:memory-bank/user-persona.md。
- **AI 干什么**:起草;人补充真实观察。
- **人干什么**:确认「这就是我要服务的人」;ToB 项目记得写购买者/决策者/使用者三类(02 文档 ToB 节)。
- **怎么算完成**:人确认 persona 可信。
- **深读**:01 文档 Stage 02。

## Step 3 竞品速览(约 1 小时,可轻量)

- **做什么**:3 个以上竞品/替代方案的矩阵 + 一句话差异点。
- **输出**:memory-bank/competitor-analysis.md。
- **AI 干什么**:检索 + 整理矩阵;人验证事实。
- **人干什么**:拍板差异点;接受「无竞品」的判断与风险。
- **怎么算完成**:差异点一句话能说清。工具型产品可缩到 1–2 页。
- **深读**:01 文档 Stage 03。

## Step 4 写 PRD(约 2 小时)

- **做什么**:FR 表(编号 + 优先级 P0/P1/P2 + 验收口径)+ NFR + 明确不做清单(带理由)。
- **输出**:memory-bank/PRD.md。
- **AI 干什么**:起草 FR 表与不做清单。
- **人干什么**:**定优先级、砍功能**;确认 P0 集合本身是一条可演示的核心闭环(≤ 5 分钟)。
- **怎么算完成**:P0 范围冻结;每个 FR 有可判定验收口径。
- **深读**:01 文档 Stage 04;模板见 05 文档 PRD 节。

## Step 5 架构三件套(约半天)

- **做什么**:依次写产品架构 → AI/Agent 设计 → 技术设计。
- **输出**:product-architecture.md + agent-design.md + technical-design.md。
- **AI 干什么**:画 ASCII 架构图、打「规则 or AI」标签、做选型对比表。
- **人干什么**:①确认**核心数据源模块**(它最先做);②确认 AI 边界(哪些绝不自动执行);③拍板付费/托管/合规选型。
- **怎么算完成**:每个 P0 FR 有归属模块;每个用 AI 的 FR 有 Agent 契约;选型有对比与理由。
- **深读**:01 文档 Stage 05/06/07;AI 产品别跳过 06——Agent 契约写不清,编码必然返工。

## Step 6 设计系统(约 2 小时,轻量版)

- **做什么**:token(色/字/间距/圆角/阴影)+ 硬约束 + 提交前自检清单。
- **输出**:design/DesignRules.md + design/DesignSystem.md(轻量可合 1 文件)。
- **AI 干什么**:起草 token 与规则。
- **人干什么**:定品牌方向;确认自检清单。
- **怎么算完成**:token 是单一事实来源;规则可用 grep 检查。
- **深读**:01 文档 Stage 08;模板见 05 文档第三节。

## Step 7 实施计划(约半天)

- **做什么**:Phase/里程碑划分 + 四段式任务清单(做什么/依赖/验证/产出物)+ 分层测试策略 + 偏差记录约定。
- **输出**:memory-bank/implementation-plan.md。
- **AI 干什么**:拆任务、写四段式、定测试策略。
- **人干什么**:确认里程碑顺序与**纵向链路模块选择**(选核心数据源模块);确认全局原则。
- **怎么算完成**:每个任务四段齐全、依赖显式;任务粒度 = 半天到一天;P0 构成完整纵向链路。
- **深读**:01 文档 Stage 09;任务模板见 03 文档第三节。

## Step 8 编码(主功能约 7 天,四小步)

每小步结束时,人亲手走一遍产品并给出反馈:

- **8a 工程地基(约 1 天)**:六根柱子——脚手架、质量门禁、token 落地、DB、认证、**LLM Mock 适配层**、Agent 基座、布局。完成 = 三个质量命令绿 + Mock 全链路可跑通(零 Key)。→ 01 文档 Stage 10
- **8b 纵向核心链路(约 1 天)**:数据层 → 表单 → Agent → 管线 → 结果页 → 纠偏。完成 = 核心闭环 ≤ 5 分钟 + **人试用满意**。→ 01 文档 Stage 11
- **8c 横向功能扩展(约 3–4 天)**:其余模块按依赖序逐个交付;复杂模块(文件解析等)留返工预算。完成 = 计划内模块全交付。→ 01 文档 Stage 12/13
- **8d 打磨与收敛(约 2 天)**:逐页走查 + IA 审视 + 性能。完成 = 走查问题清零 + 375px 无溢出。→ 01 文档 Stage 14

**编码期规则**:每个任务走 03 文档的 11 步循环;验收标准与 Blocker 判定用 04 文档;项目类型注入点用 02 文档。

## Step 9 交付(约 1 天)

- **做什么**:写 demo-flow 验收脚本 → 按它完整走一遍 → 重写 README → 截图入库。
- **输出**:docs/demo-flow.md + README + docs/screenshots/。
- **AI 干什么**:全部起草;按 demo-flow 自查。
- **人干什么**:**亲自按 demo-flow 走通全流程**(这是最终验收);部署与否拍板(可暂缓,Stage 16)。
- **怎么算完成**:demo-flow 每一步 Mock 零成本可复现;README 与事实一致(功能/测试数/截图)。
- **深读**:01 文档 Stage 15/16/17;模板见 05 文档第五节。

## 常见跳过陷阱(哪些步骤可轻量、哪些不可跳过)

| 步骤 | 可轻量到什么程度 | 不可跳过的部分 |
| --- | --- | --- |
| Step 3 竞品 | 1–2 页矩阵 | 差异点一句话(跳过的理由写进 vision) |
| Step 6 设计系统 | 合并为 1 个文件 | token 单一来源 + 自检清单 |
| Step 8a 地基 | 按技术栈裁剪 | LLM Mock 先行 + 质量门禁当天可用 |
| Step 8c 联动 | 单模块产品可并入 8c | — |
| Step 9 部署 | 整体可延后 | 人拍板而非 AI 自动部署 |
| **其余所有步骤** | — | **不可跳过**(每步都是后一步的输入,跳一步 = 后面所有决策失去依据) |

## 启动时的三件事(给未来的自己)

1. 判断项目类型(02 文档第二节),把注入点表打印进实施计划。
2. 在 vision 里写下全局验收锚点(如「核心闭环 < 5 分钟」)——它是所有后续验收的基准。
3. 记住四层边界(01 文档第三节):下一个项目的业务内容,永远不进这套 SOP 的核心。
