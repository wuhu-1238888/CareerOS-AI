# 04 阶段验收机制(Stage Acceptance)

> 版本:v1.0 | 最后更新:2026-09-07 | 配套:[01-AI-PRODUCT-DEVELOPMENT-SOP.md](01-AI-PRODUCT-DEVELOPMENT-SOP.md)

**定位**:定义「一个 Stage / 一个任务怎么算完成」。01 文档中 17 个 Stage 条目的「验收标准 / 测试方式 / 进入下一阶段条件」三栏都使用本文件的模板与判定规则。

---

## 一、Stage 验收模板(8 字段)

每个 Stage 按以下 8 字段验收;Stage 内的每个任务是其缩小版(CareerOS 的四段式任务模板:做什么 / 依赖 / 验证 / 产出物)。

| 字段 | 含义 | 填写时机 |
| --- | --- | --- |
| 目标 | 本阶段要达成的**可观察结果**,不含实现细节 | 实施计划(Stage 09) |
| 输入 | 依赖的上游文档 / 上一阶段产物,**显式列出,不可跳过** | 实施计划 |
| 任务 | 拆解后的任务列表,每个任务 = 一次独立工作会话(半天到一天) | 实施计划 |
| 输出 | 代码 + 文档 + 测试的具体产物清单 | 实施计划,执行中修订 |
| 验收标准 | 可判定的通过条件(见第四节「怎么写好验收标准」) | 实施计划,执行中修订 |
| 测试方式 | 分层测试(见第二节)中选哪几层 + 手工走查项 | 实施计划 |
| 文档更新 | 完成后必须更新的文档(progress 等) | 执行时 |
| 退出条件 | 通过 / 带遗留通过 / 不通过(见第五节) | 执行时 |

> CareerOS 证据:implementation-plan.md 的任务模板(做什么 / 依赖 / 验证 / 产出物)与每个任务的验收标准;progress.md 每 Stage 末的「完成情况表(任务/内容/状态/commit)+ 主要修改 + 测试结果 + 已知问题(遗留)+ 下一步」。

## 二、分层测试策略(5 层)

任何 Stage 的「测试方式」都从这张表选择,不允许发明第六层。

| 层 | 对象 | 工具 | 必须覆盖的用例 | CareerOS 证据 |
| --- | --- | --- | --- | --- |
| L1 纯逻辑 | 算法、规则、工具函数 | Vitest 单测 | 正常 + 边界 + 非法输入 | src/lib/resume/__tests__/ats-rules.test.ts |
| L2 API | tRPC / REST 接口 | Vitest + 直连 caller | **成功 + 鉴权失败 + 越权 + 非法参数** 四类缺一不可 | implementation-plan.md 测试策略表 |
| L3 UI 组件 | 交互组件 | Vitest + Testing Library | 渲染 + 交互 + 状态分支 | src/components/ui/__tests__/ |
| L4 UI 页面 | 整页布局 / 响应式 | **手工走查** + DesignRules 自检清单 | 视觉、间距、375px 横向溢出、断点 | design/DesignRules.md「提交前自检清单」12 条 |
| L5 AI 输出 | Agent / 管线输出 | **固定样例集回归** | 输入固定标注样例 → 跑 → schema 校验 + 标注一致;改 Prompt 后必须重跑 | implementation-plan.md「AI 输出→固定样例集测试」 |

要点:

- **测试随功能提交,不设独立测试阶段**:CareerOS 的 935 个用例中 99% 内嵌在功能提交里,唯一独立 test 提交(`1591d61`)是修偶发超时。测试写在任务「验证」段里。
- **L5 是 AI 产品特有的层**:LLM 输出不稳定的产品,样例集回归是唯一能防止「改 Prompt 把别的功能改坏」的机制。
- **L4 不可省略**:自动化测不出「丑」和「溢出」,CareerOS 走查期(9/4–9/7)的 26 个提交全部是 L4 层问题。

## 三、验收执行流程(每个任务结束后的固定动作)

按顺序执行,任何一步不过就返回修复,不允许带着失败进下一步:

1. **自动测试**:跑本任务相关测试文件 + 全量测试(全量只在阶段末跑;偶发失败需复跑两轮确认,如 `1591d61` 的处置方式)
2. **类型与规范门禁**:`typecheck`(tsc --noEmit)+ `lint`
3. **设计规则自检**:按 DesignRules 自检清单逐条核对,含 grep 检查(如无新增硬编码色值)
4. **走查**:新页面跑一遍真实浏览器(响应式 375px + 桌面),记录走查结论到 DesignRules「走查记录」
5. **文档同步**:progress.md 勾选任务 + 写状态行(见下)+ 偏差记录
6. **Git**:按 CLAUDE.md 纪律提交(见 03 文档)

> CareerOS 证据:Stage 6 的验收记录 commit `5bdea56`「record Stage 6 engineering acceptance run (703/703, typecheck/lint clean)」——质量门禁以记录形式存在,而不是 CI 自动拦截。

## 四、怎么写好验收标准(可判定,不可形容词)

| 坏例子(不可判定) | 好例子(可判定) |
| --- | --- |
| 「页面看起来不错」 | 「375px 下无横向滚动(scrollWidth ≤ clientWidth),标题区→内容间距 40–48px」 |
| 「AI 输出合理」 | 「10 个固定样例全部通过 schema 校验,且 3 个手工标注样例的排序/字段与标注一致」 |
| 「性能可以」 | 「画像分析全程 < 15s,简历 < 30s(Mock 模式)」 |

规则:验收标准必须回答「跑什么命令、看什么数值、通过阈值是多少」。写不出来的标准 = 还没想清楚。

> CareerOS 证据:Phase 1 验收标准 6 条含明确性能阈值(画像<15s、简历<30s);Task 8 间距优化的验收用 boundingBox 实测值(24/48/40px)而非「间距合理」。

## 五、Blocker vs 遗留:什么时候必须停下来

### Blocker(必须停下修复,不允许带病进入下一阶段)

| 类别 | 判据 | CareerOS 实例 |
| --- | --- | --- |
| 数据错误 | 落库数据错、用户数据丢失风险 | 4.10 模块乱序(提取层视觉排序修复 `b34c334`) |
| 状态卡死 | 用户操作后卡在中间态,需手动刷新 | 4.17 进度卡死(`0b04757`)、画像轮询钉死(`5468f81`) |
| 鉴权漏洞 | 未登录可访问受保护资源 | middleware 保护名单缺 /resumes(`e64a978`) |
| 验收断言不过 | 阶段验收标准有任一不通过 | 4.11「更换简历」验收被否,返工为「上传=新增独立简历」 |
| 关键链路断裂 | 核心闭环某一步走不通 | — |

### 遗留(记录编号,继续前进,阶段末汇报)

| 类别 | 判据 | CareerOS 实例 |
| --- | --- | --- |
| 性能优化 | 达标但可更快 | 历史消息跳过打字机空转(`7669f32`,perf 而非 blocker) |
| 增强功能 | 计划外的好主意 | 深色模式、分享卡(排入后置增强) |
| 外部依赖 | 缺凭证 / 缺真实环境 | 微信登录缺 AppID 暂缓(6.7)、真实 DeepSeek Key 未验证 |
| 部署 | 可延后的发布动作 | 生产部署用户拍板暂缓 |
| 样式打磨 | 不影响功能的视觉问题 | 走查期统一处理(先功能后视觉) |

### 判定规则

1. 一个问题是 Blocker 还是遗留,**由人判定**,AI 只能分类建议、不能自行降级 Blocker。
2. 带遗留通过是常态,不是失败;「零遗留」不值得追求——把增强功能当 Blocker 会导致永不过阶段。
3. 遗留必须进入**编号滚动清单**(见下),否则等于消失。

## 六、遗留问题管理(编号滚动清单)

模板(CareerOS progress.md 的实际形式):

```
## 未解决的问题(遗留)
| # | 问题 | 影响范围 | 处置计划 | 状态 |
| #1 | 真实 DeepSeek Key 未验证 | 全管线 | 上线前用真实 Key 跑样例集 | 开放 |
| #2 | ... | ... | ... | 开放/已解决 |
```

规则:

- 每个 Stage 结束,清单必须被更新(新增 / 解决 / 延期)——「不隐瞒」是硬规则,progress.md 的「已知问题(遗留,不隐瞒)」一节就是为此存在。
- 清单随 progress.md 一起走,是下次会话的输入(避免 AI 或人遗忘)。
- 已解决的问题移入「已解决的问题」清单保留根因与修复记录,不删除。

## 七、AI 输出验收:固定样例集机制(展开)

这是 L5 层的操作细则,所有含 LLM 的 Stage 都适用:

1. **建样例集**:人手工挑选/构造 5–20 个代表性输入,人手工标注期望输出(排序、字段值、边界)。
2. **提交入库**:样例与标注作为测试夹具提交仓库,不是临时脚本。
3. **每次改 Prompt / 换模型 / 改管线后重跑**:断言 = schema 校验通过 + 与标注一致。不一致即失败,必须修 Prompt 或管线。
4. **真实模型补充验证**:Mock 模式保证开发不受 Key 约束;真实 Key 到位后再跑同一样例集,拦截 Mock 掩盖的问题。

> CareerOS 证据:implementation-plan.md「AI 输出→固定样例集测试」;真实 DeepSeek 违规自报优先级被样例集拦截后,改为 transform 确定性归一化(不信任模型自报,`1c6e5f5`);README「测试集中大量 AI 输出固定样例回归」。
