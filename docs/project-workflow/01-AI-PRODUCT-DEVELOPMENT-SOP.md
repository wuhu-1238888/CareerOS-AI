## 一、定位与适用范围

**是什么**:一套「AI 产品从 0 到 1 应该被怎样分析、设计、实现、验证、交付」的通用开发框架。核心流程与具体业务无关。

**不是**:

- 不是 CareerOS 项目复盘(CareerOS 的内容只作为「证据」出现)
- 不是 ToB / ToC 等任何单一类型的 SOP(类型差异在 02 文档的适配层)
- 不是理论文章:每个阶段都回答「做什么 / 为什么做 / 产出什么 / AI 能帮什么 / 人判断什么 / 怎么知道完成」

**怎么用**:新项目启动从 [06-QUICK-START](06-QUICK-START.md) 进入;遇到细节回到本文件与 02/03/04;搭目录骨架用 05。

## 二、核心原则(5 条,来自 CareerOS 实践)

| # | 原则 | 含义 | CareerOS 证据 |
| --- | --- | --- | --- |
| 1 | **先跑通再完善** | 先做最小可用闭环,后置增强排在链路之后;任何时刻产品都是可演示的 | implementation-plan.md 全局原则;M2 画像先闭环,深色/分享卡后置 |
| 2 | **每步可验证** | 每个任务有可判定的验证方式(自动测试或手工检查),无验证任务不排期 | 任务四段式模板的「验证」段 |
| 3 | **数据优先** | 数据模型先于 UI;核心数据源模块先于消费方模块 | 「先纵后横」中纵向链路 = 数据源模块 |
| 4 | **设计约束优先** | UI 决策受 DesignRules 硬约束,不自由发挥 | DesignRules.md 禁令 + 提交前自检清单 |
| 5 | **小步提交** | 单任务单会话、单任务单 commit,阶段末统一收尾 | 138 提交 / 21 天,feat 连发 + 阶段 docs 收尾 |

## 三、四层边界(本套 SOP 最重要的分类规则)

任何经验、文档、流程落入新项目前,先问「它属于哪一层」:

| 层 | 定义 | 处置 | CareerOS 实例 |
| --- | --- | --- | --- |
| **Universal Core** | 任何 AI 产品都适用 | 进入本文件的核心流程 | 四段式任务、分层测试、Mock 先行、先纵后横、阶段收尾、偏差记录、git 纪律、demo-flow 验收 |
| **Project-Type Adaptation** | 只适用某类产品(ToB/ToC/ToG/AI 工具/Agent) | 进 02 文档,按类型注入 | 角色权限(ToB)、留存增长(ToC)、合规审计(ToG) |
| **Project-Specific** | 只属于某个产品 | 排除,仅作举例 | 职业画像、岗位匹配、ATS 规则、微信登录、求职域数据模型 |
| **Optional** | 不是所有项目都需要 | 标注「可选」,按需启用 | 深度竞品分析、部署、深色模式、埋点、README 美化 |

**误判的代价**:把 Project-Specific 当 Universal → 下一个项目被上一个项目的业务绑架;把 Universal 当 Optional → 丢掉真正值钱的方法。判定问一句:「换个完全不同的产品,这条还成立吗?」不成立就是 Specific。

## 四、开发管线总览:4 Phase × 17 Stage

```
Phase 1 定义       Phase 2 设计          Phase 3 实施(AI Coding 主力区)      Phase 4 交付
01 项目定义   →   05 产品架构      →    10 工程地基        →              15 交付与演示
02 用户与场景 →   06 AI/Agent 设计 →    11 纵向核心链路    →              16 部署与观测(可延后)
03 竞品与市场 →   07 技术设计      →    12 横向功能扩展    →              17 复盘与沉淀
04 PRD        →   08 设计系统      →    13 集成与联动
                  09 实施计划      →    14 打磨与收敛
```

- Phase 1–2 全部是**文档工作**(AI 起草、人拍板),Phase 3 是**编码**(AI 执行、人验收),Phase 4 是**交付与沉淀**。
- 测试与 Git 不设独立阶段:两者是**横切机制**(测试内嵌每个任务,git 纪律全程生效),细则见 04 与 03。
- 每个 Stage 条目格式:目标 / 输入 / 核心工作(AI 做什么 · 人做什么)/ 输出物 / 验收标准 / 测试方式 / 文档更新 / 进入下一阶段条件 / CareerOS 证据。

## 五、17 个 Stage 完整条目

### Phase 1 定义(产品是什么)—— 纯文档,人拍板密度最高

### Stage 01 项目定义

- **目标**:一页纸说清——为谁解决什么问题、为什么是现在、成功长什么样、明确不做什么。
- **输入**:人的想法(唯一允许零文档输入的阶段);AI 以访谈式提问引导。
- **核心工作**:AI 提问澄清(目标用户/核心问题/替代方案/成功度量)→ 人回答 → AI 起草 vision → 人逐条修改拍板。
- **输出物**:memory-bank/product-vision.md(定位一句话、核心问题、成功标准(可度量)、边界)
- **验收标准**:四要素齐全;成功标准是可度量的(不是「受欢迎」而是「注册→核心闭环 < 5 分钟」);人对边界无异议。
- **测试方式**:无(文档阶段,人审阅即验收)。
- **文档更新**:创建 product-vision.md。
- **进入下一阶段条件**:人对「做什么/不做什么/成功标准」无异议。
- **CareerOS 证据**:memory-bank/product-vision.md;Phase 1 目标「注册→画像→路线图→简历→导出全链路 < 5 分钟」是全局验收锚点。

### Stage 02 用户与场景

- **目标**:明确典型用户是谁(1–3 个 persona)、在什么场景用什么、最大痛点。
- **输入**:vision。
- **核心工作**:AI 起草 persona(画像/目标/使用场景/痛点/当前替代方案)→ 人补充真实观察、确认「这就是我要服务的人」。
- **输出物**:memory-bank/user-persona.md。
- **验收标准**:每个 persona 有场景与痛点(不是人口学标签堆砌);人确认目标用户无歧义。轻量产品 1 个 persona 足够,不为完整而凑数。
- **测试方式**:无。
- **文档更新**:创建 user-persona.md。
- **进入下一阶段条件**:人确认 persona 可信。
- **CareerOS 证据**:memory-bank/user-persona.md(独立于 vision 的画像文档)。

### Stage 03 竞品与市场(可轻量)

- **目标**:确认空间存在 + 找到差异化卡位。不是写论文。
- **输入**:vision + persona。
- **核心工作**:AI 检索整理竞品矩阵(核心功能/定价/目标用户/AI 能力)→ 人验证事实、拍板差异点。
- **输出物**:memory-bank/competitor-analysis.md(竞品矩阵 + 一句差异点)。
- **验收标准**:≥ 3 个竞品或替代方案的矩阵;差异点一句话能说清;无真实竞品时明确写出「蓝海/伪需求」判断与理由。
- **测试方式**:无。
- **文档更新**:创建 competitor-analysis.md。
- **进入下一阶段条件**:差异点得到人确认;若判断「无竞品」也须人确认接受该风险。
- **CareerOS 证据**:memory-bank/competitor-analysis.md 竞品矩阵。
- **轻量条件**:工具型/内部型产品可缩到 1–2 页;跳过的理由须写进 vision 边界。

### Stage 04 PRD(含问题与需求分析)

- **目标**:把「想做什么」变成具体功能清单(带优先级)+ 明确不做清单(带理由)。
- **输入**:01/02/03 三份文档。
- **核心工作**:AI 起草 FR 表(编号、描述、优先级 P0/P1/P2、验收口径)+ NFR → **人定优先级、砍功能**;明确不做清单每项必须带来源与理由。
- **输出物**:memory-bank/PRD.md。
- **验收标准**:每个 FR 有编号 + 优先级 + 可判定验收口径;「明确不做」清单每项带理由;人确认 **P0 集合本身构成一条可演示的核心闭环**(≤ 5 分钟跑完)。
- **测试方式**:无。
- **文档更新**:创建 PRD.md。
- **进入下一阶段条件**:P0 范围冻结(后续新增需求一律进 P1/P2 或不做清单)。
- **CareerOS 证据**:PRD.md FR 表带优先级;「明确不做/延后」10 项各带来源(如 FR-30);Phase 1 的 5 分钟闭环目标。
- **为什么不单设「问题与需求分析」阶段**:CareerOS 没有独立的问题分析文档,问题陈述分布在 vision/persona/PRD 三处;单设阶段会造成文档重复。问题定义是 PRD 的开篇章节。

### Phase 2 设计(怎么建)—— 文档工作,决定后面所有返工成本

### Stage 05 产品架构

- **目标**:模块划分与数据流——哪些模块、谁喂谁、联动关系,**并找出核心数据源模块**。
- **输入**:PRD。
- **核心工作**:AI 画信息架构 / 模块依赖图 / 数据流(ASCII 图)→ 人确认模块边界合理、无循环依赖。
- **输出物**:memory-bank/product-architecture.md。
- **验收标准**:每个 P0 FR 能落到某个模块;模块数据流有向无环;**核心数据源模块被显式标出**(它是纵向链路阶段的执行对象)。
- **测试方式**:无。
- **文档更新**:创建 product-architecture.md。
- **进入下一阶段条件**:人确认「核心数据源模块」选择正确——所有下游模块都消费它,它必须最先做。
- **CareerOS 证据**:product-architecture.md ASCII 架构图与联动表;画像被选为纵向链路模块,因为路线图/简历/匹配/面试全部消费画像数据(git 顺序证明)。

### Stage 06 AI/Agent 设计(AI 产品特有阶段)

- **目标**:决定 **AI 用在哪、不用在哪**;每个 Agent 的分工与输入输出契约、失败处理、Human-in-the-loop 点。
- **输入**:PRD + 产品架构。
- **核心工作**:AI 逐 FR 打「规则 or AI」标签(可计算/需确定性的用规则,生成/分析类的用 AI)→ 设计 Agent 契约(输入/输出 schema/失败策略)→ 标注每个决策点「AI 建议人裁决」或「AI 自动执行」→ 人确认 AI 边界(哪些绝不自动执行)。
- **输出物**:memory-bank/agent-design.md。
- **验收标准**:每个用 AI 的 FR 有对应 Agent 契约;每个关键决策点标注裁决方式;AI 输出有评测方式(固定样例集,见 04 文档 L5 层);「规则 or AI」判定记录在案。
- **测试方式**:无(评测设计在 Stage 11 落地为样例集测试)。
- **文档更新**:创建 agent-design.md。
- **进入下一阶段条件**:人确认 AI 边界清单(哪些自动执行、哪些必须人裁决)。
- **CareerOS 证据**:agent-design.md 11 Agent + echo 交叉校验 + 人裁决点;「确定性归一化,不信任模型自报」(`1c6e5f5`);纠偏 = AI 建议人裁决,任务状态切换 = 自动执行。
- **这是 AI 产品与普通产品最大的设计差异**:Agent 契约写不清楚,编码阶段必然返工。

### Stage 07 技术设计

- **目标**:选型 + 数据模型 + API 约定,保证编码阶段不推倒重来。
- **输入**:产品架构 + Agent 设计。
- **核心工作**:AI 做选型对比表(候选/优劣/结论)、数据模型、API 层约定(错误码/鉴权/流式)、安全策略 → **人确认**(付费项、托管、合规类选型必须人拍板)。
- **输出物**:memory-bank/technical-design.md。
- **验收标准**:每个选型有对比与理由;数据模型覆盖产品架构全部实体;API 约定明确到可编码。
- **测试方式**:无。
- **文档更新**:创建 technical-design.md。
- **进入下一阶段条件**:人确认选型(付费/托管/合规项)。
- **CareerOS 证据**:technical-design.md 选型对比表;「实施架构决策补记」章节(七至十三章)——选型定了不回改,实施偏差往补记里写。

### Stage 08 设计系统

- **目标**:把 UI 决策变成**可执行规则**,防止 UI 漂移(越改越乱、每页一个样)。
- **输入**:persona + PRD。
- **核心工作**:人定品牌方向与风格参考 → AI 起草 token(色/字/间距/圆角/阴影)+ 设计规则(硬约束 + 提交前自检清单)→ 人确认。
- **输出物**:design/DesignRules.md + design/DesignSystem.md。
- **验收标准**:token 是**单一事实来源**(代码引用它,禁止硬编码偏离值);规则是可执行禁令(能用 grep 检查)不是形容词;有提交前自检清单。
- **测试方式**:无。
- **文档更新**:创建 design/ 两个文件。
- **进入下一阶段条件**:人确认品牌方向与 token。
- **CareerOS 证据**:DesignSystem.md front matter = token 单一事实来源;DesignRules.md 自检清单 12 条 + 硬编码色值 grep 命令;dev/tokens 可视化核对页。
- **可选裁剪**:轻量产品可合并为 1 个文件,但「token 单一来源 + 自检清单」两件事不可省。参考分析(Atlassian.md/Linear.md 这类第三方设计方法论分析)是 Optional,不是必需。

### Stage 09 实施计划(Implementation Plan)

- **目标**:把 05–08 的设计变成**可执行任务清单**,并定义节奏、验收与偏差处理规则。
- **输入**:05/06/07/08 四份文档。
- **核心工作**:AI 划分 Phase/里程碑、写四段式任务(做什么/依赖/验证/产出物)、分层测试策略、全局原则 → **人确认里程碑顺序与纵向链路模块选择**。
- **输出物**:memory-bank/implementation-plan.md。
- **验收标准**:每个任务四段齐全、依赖显式、验证可判定;任务粒度 = 一次独立工作会话(半天到一天);P0 任务构成完整纵向链路;里程碑有验收标准(参照 04 文档模板);含偏差记录约定与「明确不做」清单。
- **测试方式**:无。
- **文档更新**:创建 implementation-plan.md。
- **进入下一阶段条件**:人确认计划(特别是纵向链路模块 + 里程碑顺序)。
- **CareerOS 证据**:implementation-plan.md 任务模板(line 11-18)、分层测试策略表(line 20-28)、全局原则 5 条(line 500-507)、偏差记录约定(line 41-43)、「每个任务 = 一次独立工作会话」。
- **偏差记录约定**(本套 SOP 继承):执行中与上游文档不一致 → 在实施计划显式标注 → 「执行以计划为准,不回头改上游文档」→ 阶段末三处同步(计划状态行 / technical-design 补记 / progress)。

### Phase 3 实施(AI Coding 主力区)—— 每个任务遵循 03 文档的 11 步循环

### Stage 10 工程地基

- **目标**:一天立「六根柱子」——脚手架、质量门禁、设计 token 落地、DB、认证、**LLM 适配层(Mock 先行)**、Agent 基座、布局骨架。所有业务建在其上。
- **输入**:07/08/09。
- **核心工作**:AI 执行(纯 AI 执行区,人只确认);顺序:脚手架 → 设计 token → DB → 认证 → LLM Mock → Agent 基座 → 布局 → 设置页。
- **输出物**:可运行空壳 + 测试基建 + DB 迁移与种子 + 质量命令(lint/typecheck/test)。
- **验收标准**:三个质量命令可用且绿;**Mock 模式下全链路可跑通(零 API Key)**;token 落地后 grep 无硬编码偏离值;种子脚本幂等(重复执行不脏数据)。
- **测试方式**:L1/L2/L3 基建就绪 + 冒烟走查。
- **文档更新**:progress.md 记录地基完成与遗留。
- **进入下一阶段条件**:人确认空壳可运行、Mock 链路可跑通。
- **CareerOS 证据**:M1 一天 8 提交(`b463c2f` 脚手架 → `33d623c` token → `5a809ee` DB → `cc7c14d` 认证 → `ec5d63f` LLM Mock → `5c20efd` Agent 基座 → `7c92c47` 布局);prisma/seed.ts 幂等「先清理再重建」。
- **为什么 Mock 先行是铁律**:LLM 适配层做成可插拔,Mock 为默认提供方——开发、测试、演示全部零成本,真实 Key 到位后无缝切换(CareerOS 全程 Mock 可跑通,README 明示「零 API 成本」)。

### Stage 11 纵向核心链路

- **目标**:选一条最核心用户链路**端到端打通**,形成可演示的最小闭环。这是整个开发过程价值密度最高的一步。
- **输入**:09 的计划 + 10 的地基。
- **核心工作**:按依赖序交付:**数据层 → 表单 → Agent → 管线 → 结果页 → 纠偏反馈**;每个子任务四段式 + 内嵌测试。
- **输出物**:可演示闭环(如 CareerOS:注册 → 画像采集 → 分析 → 结果 → 纠偏)。
- **验收标准**:闭环全程 ≤ 5 分钟;每个子任务测试绿;**人亲手走一遍并给出试用反馈**;链路 UX 问题(手风琴、字段缺失等)在进入横向扩展前解决。
- **测试方式**:L1–L5 全层 + 真人试用走查。
- **文档更新**:progress.md 逐任务勾选 + 阶段收尾(完成表/遗留)。
- **进入下一阶段条件**:人试用满意(或反馈已全部处置)。
- **CareerOS 证据**:M2 画像单日 9 提交(2.1 数据 → 2.2 表单 → 2.3 Agent → 2.4 管线 → 2.5 结果页 → 2.6 纠偏 → 2.7 更新联动);用户试用发现漏字段 → 「2.2 补遗:经历时长」;手风琴 UX 被用户反馈推翻重做(`d15eca8`)。
- **为什么先纵后横**:纵向链路上暴露的每一个问题(数据缺字段、Agent 输出不稳定、UX 不通)都会在横向 5 个模块里被复制 5 次;先修 1 次再铺 5 次。

### Stage 12 横向功能扩展

- **目标**:其余模块按依赖序逐个交付,每个模块遵循同一依赖序(数据层 → 表单 → Agent → 管线 → UI)。
- **输入**:11 的闭环 + 09 的其余任务。
- **核心工作**:单模块单日交付节奏;模块内依赖序;每模块末 docs 收尾(完成表 + 遗留)。
- **输出物**:全部功能模块(每个带测试)。
- **验收标准**:每模块验收标准通过 + 测试绿;**含文件解析/多外部系统的复杂模块在计划时留「返工预算」**(预期计划外任务)。
- **测试方式**:各模块 L1–L5 按 09 计划执行。
- **文档更新**:progress.md 逐任务 + 每模块收尾。
- **进入下一阶段条件**:计划内模块全部交付(遗留项除外)。
- **CareerOS 证据**:M3–Stage 6(路线图 → 简历 → 工作台 → 匹配 → 面试);简历模块计划 7 任务(4.1–4.7)实际 17 个(4.8–4.17 为验收返工与修复),**文件解析类返工率显著最高**(30 个提交 / 计划 7 任务);每阶段末 docs 收尾提交(`a6ab40e`、`7cfa218`、`1e4a53f` 等)。
- **顺序逻辑**:先做消费核心数据的模块,后做独立模块;对外部系统依赖最重的模块(如简历的文件解析)不是最后做,而是**给它留最多余量**。

### Stage 13 集成与联动

- **目标**:跨模块数据联动(全局上下文组装、冲突裁决)。单模块产品跳过或并入 Stage 12。
- **输入**:12 的全部模块。
- **核心工作**:联动表设计、全局上下文组装注入各管线、冲突呈现 UI(并列双方依据,由用户裁决)。
- **输出物**:联动服务 + 裁决 UI。
- **验收标准**:联动点有测试;冲突场景呈现双方依据而非替用户选边。
- **测试方式**:L1/L2 + L5(联动注入管线后样例集重跑)。
- **文档更新**:progress.md 记录联动实施与设计偏差。
- **进入下一阶段条件**:联动测试绿,冲突裁决 UX 走查通过。
- **CareerOS 证据**:Stage 8——新表 LinkageHint/DirectionResolution(`fb6dc3a`)、全局上下文 11 处管线注入(`f984536`)、冲突对比块(`e466f9f`)、偏差记录(`e932d19`)。
- **为什么最后做**:联动需要所有模块先存在;先做联动等于为不存在的模块写空壳。

### Stage 14 打磨与收敛

- **目标**:走查驱动的 UI 收敛 + 信息架构审视 + 性能。与功能开发**分开排期**,不混排。
- **输入**:可用且功能完整的 12/13 产物。
- **核心工作**:逐页走查(视觉/响应式/375px 横向溢出)、IA 审视(导航与信息架构)、性能修复、style+docs 成对提交(改一处记一笔)。
- **输出物**:稳定一致的产品。
- **验收标准**:走查问题清零;375px 无横向溢出;跨页 UI 节奏统一(标题区间距等);演示全程无卡顿;IA 经人确认。
- **测试方式**:L4 走查为主(参照 DesignRules 自检清单)+ L1/L2 回归。
- **文档更新**:DesignRules 走查记录;progress 打磨期记录。
- **进入下一阶段条件**:人走查通过(演示/评审无阻塞问题)。
- **CareerOS 证据**:9/4–9/7 的 26 提交——5 个 style 与 5 个 docs 成对出现(如 `942de96`+`958e37f`),IA 级重构(`b1b7df7`、`f2df295`),4 个 dashboard refactor(`318563a` 等),任务 8 间距统一(全部页面 40–48px 实测)。
- **教训**:先功能后视觉是对的,但「打磨」必须作为独立阶段排期——CareerOS 在 11 天停顿后才发现走查需求,说明打磨期应被计划而非等它自然发生。

### Phase 4 交付(把产品变成资产)

### Stage 15 交付与演示

- **目标**:把产品变成可验收、可展示的交付物。
- **输入**:14 的稳定产品。

- **验收标准**:demo-flow 每一步可在 Mock 模式零成本复现(写「基于当前代码的真实实现」,不是理想剧本);README 与实际一致(功能表/测试数/截图均为真)。
- **测试方式**:按 demo-flow 完整走一遍(这就是最终验收)。
- **文档更新**:README 重写;demo-flow 创建。
- **进入下一阶段条件**:人按 demo-flow 走通全流程。

### Stage 16 部署与观测(可延后,人拍板)

- **验收标准**:清单逐项勾选;每个配置项在部署环境中验证生效;监控与日志链路可用。
- **测试方式**:部署环境冒烟 + demo-flow 关键步。
- **文档更新**:deployment-checklist.md 勾选状态。
- **进入下一阶段条件**:人拍板(部署、暂缓或放弃均是有效决策)。
- **CareerOS 证据**:5.3 部署清单 + deployment-checklist.md;生产部署用户拍板暂缓(progress 遗留清单);部署配置静默失效的修复(`9e29eb9`——Next.js 忽略未知顶层 key,提示「配置要验证生效」)。

### Stage 17 复盘与沉淀

## 六、Human-AI Collaboration Model(人机协作模型)

### 6.1 人负责(不可委托,AI 只能提议)

| 职责 | CareerOS 证据 |
| --- | --- |
| 产品定位、目标用户、做什么不做什么 | vision/PRD 的拍板权全程在人 |
| 优先级与砍功能 | P0 冻结、FR 优先级人定 |
| 验收与返工判定 | 4.11「更换简历」验收被否 → 返工为「上传=新增独立简历」 |
| AI 边界(哪些绝不自动执行) | 纠偏=人裁决;微信登录暂缓(6.7);部署暂缓 |
| 关键 UX 拍板 | Stage 7 一次拍板 4 项(入口/题数三档/打字机渲染/即时评分) |
| 第三方凭证、付费、合规、上线 | 缺 AppID 就暂缓,不硬闯 |

### 6.2 AI 负责(可自主,人在事后检查)

| 职责 | 约束 |
| --- | --- |
| 文档起草(人在上游拍板之后) | 起草后必须人审阅 |
| 代码实现 + 测试 + debug | 技术确定性修正可自主(如 transform 归一化 `1c6e5f5`) |
| 文档同步(progress 勾选、偏差记录) | 任务末强制步骤 |
| Git 操作 | 在 CLAUDE.md 纪律内(见 03 文档第五节) |
| 走查执行与问题报告 | 结论由人验收 |

### 6.3 人如何检查 AI(5 种检查手段)

1. **验收标准对照**:可判定标准(04 文档第四节),不过即返工。
2. **亲手走查**:人必须亲自跑产品——CareerOS 的「2.2 补遗」「手风琴推翻」全是人试用发现的,没有一个是测试发现的。
3. **样例集回归**:AI 输出改动后重跑固定样例集。
4. **文档对账**:数字/路径/链接与事实核对(如 917 vs 935 的对账)。
5. **汇报审查**:每个任务末 AI 汇报「完成内容 + 测试结果 + 遗留问题」,人抽查验证。

### 6.4 触发人工决策的 6 类情形(AI 必须停下来问)

| # | 情形 | 例子 |
| --- | --- | --- |
| 1 | Scope 变化(计划外需求/改动超出任务范围) | 计划外新增功能 → 排期或进不做清单 |
| 2 | 产品语义(字段口径、业务规则歧义) | 7.1 题数口径矛盾 → 用户裁决三档模型 |
| 3 | 验收返工(交付不符合验收标准) | 4.11 → 人判定返工范围 |
| 4 | 凭证与部署(第三方 Key、上线、付费) | 微信登录/部署暂缓 |
| 5 | 设计冲突(文档间矛盾、token 冲突) | DesignRules:140 vs DesignSystem:507 留待用户裁决 |
| 6 | 遗留取舍(Blocker vs 遗留的最终判定) | 04 文档第五节:人判定,AI 只能建议 |

### 6.5 AI 可自主执行的条件(三同时)

**影响范围限于本任务 + 可逆(git 可回退)+ 无产品语义判断** → 可自主执行并在汇报中说明;否则必须「提议 → 人确认」。
