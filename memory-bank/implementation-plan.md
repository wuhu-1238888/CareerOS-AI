# CareerOS AI — 实施计划(Implementation Plan)

> 版本:v1.1 | 最后更新:2026-08-18 | 状态:Phase 1 待启动
>
> 本文档是 CareerOS AI 的**开发计划**。每一个任务 = 一次独立工作会话(约半天到一天),完成后提交代码并在 [progress.md](./progress.md) 勾选记录。

---

## 使用说明

### 任务结构约定

每个任务固定四段:

- **做什么**:清晰、具体的开发指令,不包含代码。
- **依赖**:本任务的前置任务或数据,显式列出(任务编号即建议顺序,但依赖不可跳过)。
- **验证**:验证该任务正确性的测试步骤(自动测试 + 手工检查)。
- **产出物**:任务完成时应存在的成果。

### 测试策略约定

| 层级 | 测试方式 | 工具 |
|------|----------|------|
| 纯逻辑(校验、计算、数据转换) | 单元测试:给定固定输入,断言固定输出 | Vitest |
| API 接口 | 接口测试:覆盖成功路径、鉴权失败、越权访问、非法参数 | Vitest + tRPC 直连 caller |
| UI 组件 | 组件测试:关键交互与四态渲染 | Vitest + Testing Library |
| UI 页面 | 手工走查清单:按 [design/DesignRules.md](../design/DesignRules.md) 的「提交前自检清单」逐条核对 | 走查清单 |
| AI 输出 | **固定样例集测试**:准备若干份手工标注的测试输入(放在测试数据目录),每次修改 Prompt 后重跑样例集,断言输出通过 schema 校验且与标注一致 | Vitest 断言 |

### 开发节奏约定

- **一次只做一个任务**,完成并验证通过后再开始下一个。
- 任务编号即建议顺序;里程碑(M)是一个可交付的检查点。
- 所有 UI 任务必须遵循 [design/DesignSystem.md](../design/DesignSystem.md) 的 token 与 [design/DesignRules.md](../design/DesignRules.md) 的约束。
- 基础优先:每个模块先做「最小可用」打通链路,标注「后置增强」的功能排在链路打通之后。

### API 层约定(2026-08-18 审查确认)

- CRUD 与 Agent 调用统一走 **tRPC Router**(类型安全贯穿前后端,测试用 tRPC 直连 caller);仅 NextAuth 回调与文件上传等框架必需端点使用 Route Handler(注:technical-design 3.1 / 4.2.1 的「API Routes + tRPC」两层表述不采用,偏差记录)。

### 与文档的偏差记录约定

本计划与 PRD / technical-design / DesignSystem 不一致之处(依据 2026-08-18 审查决策确认),均在任务措辞或各 Phase 的「明确不做 / 延后」清单中显式标注,执行时以本计划为准,不再回头改上游文档。

## Phase 1:核心闭环

### Phase 1 目标

跑通价值闭环:用户从注册开始,完成「职业画像 → 成长路线图 → 简历优化 → 导出」全链路,首次到第一个有价值输出 < 5 分钟。MVP 的三个 Agent(Profile / Navigator / Resume)全部可用。

### Phase 1 功能

**基础版(必须先完成)**:

- 邮箱注册登录;分步画像采集(教育/技能/经历/目标,最少必填);AI 画像生成(摘要、能力标签、优势、2-4 个推荐方向含匹配度、六维雷达、发展建议);画像纠偏重分析;画像主动更新
- 目标方向选择;AI 生成 3-4 阶段成长路线图(时间线展示);任务三态标记;「太难了/已经会了」反馈
- 简历上传(PDF/Word)或粘贴文本;AI 解析核对;逐条改写对比(改前/改后/原因);接受/拒绝;ATS 评分;导出 PDF
- 工作台 Dashboard;首页(价值主张 → 单一 CTA);个人设置页;三个模块间的数据自动流转

**后置增强(链路打通后再做,仍在 Phase 1 内)**:

- 导出 Word;简历解析失败降级为手动粘贴;路线图导出

### Phase 1 明确不做 / 延后(MVP 边界,2026-08-18 审查确认)

| 项 | 来源 | 处置 |
|----|------|------|
| 图片 OCR 解析 | PRD FR-30 标 P0 | 不做;粘贴文本降级。待数据验证后评估 |
| 微信登录 | PRD FR-01 标 P0 | 延后至 Phase 2(任务 6.7) |
| 邮箱验证码注册 | PRD FR-01 | 不做;MVP 用邮箱+密码(任务 1.4 偏差记录) |
| 从画像自动生成初版简历 | PRD 3.3.2 | 不做;待画像数据验证后评估 |
| 分享卡片 | PRD FR-15 P1 | 延后至 Phase 2(任务 6.8) |
| 深色模式 | DesignSystem「Phase 2 规划」 | 延后至 Phase 2(任务 6.9) |
| 限流/风控 | technical-design 4.2.1 提及 | MVP 不做;生产上线前评估 |
| 移动端适配 | PRD 十节 | 延后;仅保证 <768px 导航折叠可用 |
| JD 数据源自动接入 | PRD 十节 | 延后;粘贴 JD 文本先行 |
| 企业端匹配接口 | PRD 十节 | 延后;不在 MVP 范围 |

### Phase 1 开发任务

#### 里程碑 M1:项目地基(任务 1.1 – 1.8)

**任务 1.1 项目脚手架与目录结构**

- 做什么:按 [technical-design.md](./technical-design.md) 的技术栈(Next.js 14 App Router + TypeScript + Tailwind + shadcn/ui)初始化项目,并按其 4.3 节建立目录结构(app、components、lib 及其子目录、prisma 目录)。配置 ESLint 与路径别名。搭建测试框架:Vitest + Testing Library(前后端统一:纯逻辑与 Agent 用 Vitest 单测,组件用 Testing Library)。
  - 注:schema.prisma 采用**根目录 `prisma/schema.prisma` 单一位置**(Prisma 官方惯例;technical-design 4.3 目录树中同时出现 `src/lib/db/schema.prisma`,以本任务为准,偏差记录)。
- 依赖:无(起点任务)。
- 验证:开发服务器启动成功,浏览器能访问空白首页;TypeScript 编译与 ESLint 检查零错误;目录结构与文档一致(schema.prisma 仅存在于根目录 prisma/ 下);一个最小单元测试与一个最小组件测试均能跑通。
- 产出物:可运行的项目骨架 + 测试基建。

**任务 1.2 设计 token 落地**

- 做什么:把 [DesignSystem.md](../design/DesignSystem.md) front matter 的颜色、字号、圆角、间距、阴影全部定义为 Tailwind 主题与 CSS 变量,并用它们覆盖 shadcn/ui 默认主题。建一个开发专用的 token 展示页(仅开发环境可见),逐项列出全部 token 与其渲染效果。
- 依赖:任务 1.1(项目骨架)。
- 验证:token 展示页上每个色值、字号、圆角与 DesignSystem.md 一一对应;用搜索验证业务代码中无硬编码色值(DesignRules 禁止事项);token 展示页不进入生产路由。
- 产出物:主题配置 + token 展示页。

**任务 1.3 数据库 Schema 与迁移**

- 做什么:按 PRD 第八节与 technical-design 建立 Prisma Schema:User、CareerProfile(教育/技能/经历/兴趣/目标/AI 分析结果)、CareerPath(推荐方向)、Roadmap、Stage、Task、Resume、ResumeVersion、Optimization(逐条修改记录),外加 AgentRun 表记录每次 Agent 调用的输入输出摘要与耗时(观测用)。本地 PostgreSQL 就绪。
  - CareerProfile 增加**画像版本字段**(版本号 + 父版本引用,任务 2.6 / 2.7 / 6.5 依赖);
  - 六维技能雷达数据**并入 CareerProfile 的 AI 分析结果 JSON 列**(注:PRD 8.2 原列独立 SkillRadar 表,经确认 MVP 简化为 JSON 列,偏差记录)。
- 依赖:任务 1.1(项目骨架)。
- 验证:迁移执行成功;写一个种子脚本能写入并读回全部核心表;每张表的关键字段与 PRD 8.2 节一致(除上述两处偏差);删除 User 时关联数据的行为符合预期(明确级联或保留策略)。
- 产出物:Schema + 迁移 + 种子脚本。

**任务 1.4 邮箱注册登录**

- 做什么:用 NextAuth v5 实现邮箱 + 密码注册登录(认证回调 Route Handler 属 API 层约定的框架必需端点例外)。注:PRD FR-01 原写「邮箱验证码 + 微信扫码」,经确认 MVP 采用**邮箱+密码**(偏差记录);微信登录延后至 Phase 2(任务 6.7)。登录态用会话管理;受保护路由与 API 未登录时跳转/拒绝。密码只存哈希。
- 依赖:任务 1.3(User 表)。
- 验证:注册 → 登出 → 登录 → 登出全流程可走通;直接访问受保护页面被重定向到登录;查数据库确认密码字段不是明文;错误密码给出通用提示(不泄露账号是否存在)。
- 产出物:认证系统。

**任务 1.5 LLM 适配器 + Mock 实现**

- 做什么:按 technical-design 建 LLM Adapter 接口(统一的消息发送与流式接口),实现 **DeepSeek(OpenAI 兼容,开发与生产默认)**、OpenAI、Anthropic 三个适配器,以及一个 Mock 适配器(按配置返回固定结构化内容,不产生任何 API 费用)。Provider 通过环境变量切换。
- 依赖:任务 1.1(项目骨架)。
- 验证:单元测试:四个适配器对同一输入返回相同结构;Mock 适配器调用后 API 用量账单/日志显示零消耗;真实适配器(至少 DeepSeek)用一个最小请求验证连通与返回。
- 产出物:LLM 适配层(开发期默认 Mock)。

**任务 1.6 Agent 基座**

- 做什么:实现 Agent 基类(配置:名称、描述、System Prompt 路径、输入输出 Zod Schema、模型与温度)、Agent 注册表、Orchestrator(按意图路由、组装上下文、调用 Agent、保存 AgentRun 日志)、流式响应处理器。Prompt 以 Markdown 文件存放在 prompts 目录,与代码解耦。
  - **流式与结构化共存方案**:执行过程中进度文案流式推送(供分析过程页展示),最终结果一次性返回结构化 JSON 并经 Zod 校验;
  - **全局上下文对象预留「版本号 + 来源 Agent + 生成时间」字段**(为 Phase 3 任务 8.1 统一上下文铺路,Phase 1 起即写入)。
- 依赖:任务 1.3(AgentRun 表)、任务 1.5(适配器)。
- 验证:注册一个测试 Agent,调用执行后输出通过 schema 校验;进度文案以多条增量流式到达(非一次性);故意让 Mock 返回非法结构,系统给出友好错误并记录日志,不崩溃;AgentRun 表记录了本次调用。
- 产出物:Agent 框架基础层。

**任务 1.7 应用布局骨架**

- 做什么:按 DesignSystem 的「页面解剖学」实现:顶栏(64px,logo + 四个一级入口:工作台/职业画像/成长路线/简历优化 + 头像)、1160px 居中容器、页面头组件(标题/描述/右侧主行动)、四个模块的空白占位页与路由。
- 依赖:任务 1.2(设计 token)、任务 1.4(登录态与头像)。
- 验证:四个路由可访问,当前入口在顶栏高亮;窗口缩到 768px 以下入口折叠为抽屉;布局与 DesignRules 导航规则一致(无侧栏、无渐变);焦点环与键盘可达性正常。
- 产出物:应用外壳。

**任务 1.8 个人设置页**

- 做什么:设置页(顶栏头像下拉进入,覆盖 PRD FR-02):修改昵称/头像/密码;预留「简历文件管理」区块——待任务 4.1 完成后接入(已上传文件列表 + 删除按钮,删除后服务端文件同步清理)。
- 依赖:任务 1.4(登录态)、任务 1.7(顶栏头像)。
- 验证:昵称修改后顶栏/问候行同步;密码修改后旧密码失效、新密码可登录;「简历文件管理」区块在 4.1 完成前显示空态而非报错;走查 DesignRules 自检清单。
- 产出物:设置页。

#### 里程碑 M2:Career Profile(任务 2.1 – 2.7)

**任务 2.1 画像数据与 API**

- 做什么:实现 CareerProfile 与 CareerPath 的增删改查 tRPC Router(创建、读取、更新、删除),用户只能访问自己的数据;字段与 PRD 8.2 一致(含任务 1.3 的版本字段与 JSON 列偏差)。
- 依赖:任务 1.3(Schema)。
- 验证:接口测试覆盖:创建 → 读取 → 更新 → 删除全流程字段完整;未登录请求被拒绝;用户 A 无法读取用户 B 的画像(越权测试)。
- 产出物:画像数据层。

**任务 2.2 分步采集表单**

- 做什么:四步表单(教育背景 → 技能 → 经历 → 兴趣与目标),每步 3-5 个字段、每步顶部一句话解释「为什么需要这个信息」;必填仅学历 + 专业 + 技能,经历与目标可跳过;技能支持从预设列表选择 + 自由输入 + 熟练度分级;表单草稿随输入保存,刷新不丢;底部固定「上一步/下一步」。
- 依赖:任务 2.1(数据 API)、任务 1.7(布局)。
- 验证:手工走查:逐步填写到完成、跳过可选项、中途刷新恢复草稿;必填缺失时不允许下一步且提示具体字段;输入校验(邮箱/日期等)在失焦时提示。
- 产出物:画像采集页。

**任务 2.3 Profile Agent(Prompt + 结构化输出)**

- 做什么:在 prompts 目录编写 Profile Agent 的 System Prompt(遵循 agent-design 2.1 节:角色锚定、能力提炼、方向推荐、差距识别、边界限制、不确定性表达),定义输出 Schema(画像摘要、能力标签列表、优势 3-5 项、推荐方向 2-4 个各含匹配度与理由、六维雷达评分、发展建议、置信度)。实现 Agent 执行逻辑与输出解析。
- 依赖:任务 1.6(Agent 基座)。
- 验证:固定样例集测试:准备 3 份手工标注的背景输入(如「计算机专业应届生,会 Python」),运行 Agent,断言输出通过 schema 校验、方向推荐与标注一致、置信度随信息完整度变化;边界测试:只提供必填字段时正常输出且置信度较低,不报错。
- 产出物:Profile Agent + Prompt 文件 + 样例集。

**任务 2.4 分析过程页**

- 做什么:表单提交后进入分析页:Agent 卡 + 进度条 + 文案轮播(「正在理解你的背景…」),完成后跳转结果页。进度文案按任务 1.6 的流式方案逐条推送。任务状态持久化:分析中刷新页面可恢复查看结果或继续等待;失败展示错误原因与「重试」按钮。
- 依赖:任务 2.2(表单)、任务 2.3(Profile Agent)。
- 验证:用 Mock 慢速响应验证进度文案逐条流式出现且进度可见;分析中刷新后不丢失任务;模拟失败(错误配置)时显示友好错误与重试,重试成功进入结果页。
- 产出物:分析过程页。

**任务 2.5 画像结果页**

- 做什么:按 DesignSystem「Skill Dashboard」与 DesignRules「职业画像页」规格实现结果页:概要文字卡、优势/不足双列、能力雷达图(Recharts,六维)、推荐方向卡(匹配度大数字 + 理由)、发展建议;页面头右侧主行动「规划成长路线」,次级「优化简历」;常驻「这不是我」按钮。
- 依赖:任务 2.3(Profile Agent 输出)、任务 2.1(画像 API)。
- 验证:走查 DesignRules 自检清单;页面渲染数据与 API 返回一致;推荐方向 2-4 个且匹配度在 0-100;无画像数据时显示空状态而非报错。
- 产出物:画像结果页。

**任务 2.6 纠偏流程**

- 做什么:「这不是我」→ 弹窗让用户选择不准确的部分(方向/能力/优势)→ 提交后重新调用 Profile Agent **全量重算**(复用任务 2.4 管线,保证摘要/雷达/推荐方向整体一致;经确认不采用增量重算)→ 生成新画像版本,保留历史版本与版本号。
- 依赖:任务 2.4(分析管线)、任务 2.5(结果页入口)、任务 1.3(画像版本字段)。
- 验证:纠偏后生成新版本且旧版本仍可查看;纠偏后画像各区块(摘要/雷达/推荐方向)整体更新且互相一致;纠偏入口全程可见且可多次使用。
- 产出物:画像纠偏闭环。

**任务 2.7 画像主动更新**

- 做什么:画像页提供「更新信息」入口(覆盖 PRD FR-14 与 PRD 5.2 回访流程):回访用户修改教育/技能/经历/目标任一项 → 提交后走全量重算管线(复用任务 2.4 / 2.6)生成新画像版本;Dashboard 问候行对「信息有变化」的用户提示「建议更新画像」。
- 依赖:任务 2.6(全量重算管线)、任务 2.2(采集表单复用)。
- 验证:修改任一字段后生成新版本、版本号递增、旧版本仍可查看;提示只出现在已有画像且信息变化的回访用户场景;全流程手工走查 < 3 分钟。
- 产出物:画像主动更新闭环。

#### 里程碑 M3:Career Navigator(任务 3.1 – 3.5)

**任务 3.1 路线图数据与 API**

- 做什么:实现 Roadmap、Stage、Task 三层嵌套数据的 tRPC Router;阶段带排序字段,任务带三态状态与排序。
- 依赖:任务 1.3(Schema)。
- 验证:接口测试:创建路线图 → 追加阶段 → 追加任务 → 更新任务状态 → 读取完整嵌套结构;越权与未登录测试同 2.1。
- 产出物:路线图数据层。

**任务 3.2 目标方向选择页**

- 做什么:有画像的用户默认展示画像推荐的 2-4 个方向(带匹配度);无画像用户可直接手动输入方向;附加输入:每周可投入时间(小时)、当前阶段自评(完全新手/有一定基础/接近入门)。
- 依赖:任务 2.1(画像推荐方向)、任务 1.7(布局)。
- 验证:有画像时推荐方向带出且可切换;无画像时手动输入路径可走通;每周投入时间必填且有合理范围校验。
- 产出物:方向选择页。

**任务 3.3 Navigator Agent**

- 做什么:按 agent-design 2.2 节编写 Navigator Agent Prompt 与输出 Schema:路线图概要(总时长/阶段数)、3-4 个阶段(名称、目标、学习内容 3-5 项、实践项目 1-2 个含产出物、资源推荐、能力检查点、预估时长)。输入包含画像能力标签、目标方向、每周投入时间、当前阶段。另支持**按阶段重新生成**模式:输入限定为单个阶段(该阶段原始输入 + 用户反馈),仅输出该阶段的新内容(任务 3.5 依赖此模式)。
- 依赖:任务 1.6(Agent 基座)。
- 验证:固定样例集:同一输入固定方向跑 2 次,阶段数与结构一致;阶段数在 3-4;每阶段任务 3-8 条;修改「每周投入时间」后预估时长随之变化;实践项目均包含「产出物」描述(agent-design 的核心设计理念);单阶段重新生成样例:指定某阶段后仅返回该阶段,结构完整且不包含其他阶段。
- 产出物:Navigator Agent + Prompt + 样例集。

**任务 3.4 路线图时间线页**

- 做什么:按 DesignSystem「Career Roadmap」规格:顶部 sticky 概要条(「从 X 到 Y 的 N 个月路径」+ 总进度)、纵向时间线、阶段卡默认折叠(标题 + 时长 + 任务进度徽章)、展开显示目标/学习内容 Tag/实践项目/检查点/任务列表。
- 依赖:任务 3.1(数据 API)、任务 3.3(Navigator Agent)、任务 2.4(复用分析过程模式)。
- 验证:展开折叠正常;时间线节点状态(完成/当前/未来)与任务进度联动;走查 DesignRules「职业路线页」页面规则;生成中状态复用 2.4 的分析过程模式。
- 产出物:路线图页。

**任务 3.5 任务状态标记与反馈**

- 做什么:任务三态切换(待开始/进行中/已完成,可撤销);每个任务附「太难了」「已经会了」反馈按钮;点击反馈后调用 Navigator Agent 仅重新生成该阶段内容(其他阶段不变)。任务状态**服务端持久化**,刷新后保留(注:technical-design 5.2 原写「本地状态、手动标记」,经确认采用服务端持久化,偏差记录)。
- 依赖:任务 3.4(路线图页)、任务 3.3(单阶段重新生成)。
- 验证:状态切换即时反映且刷新后保留;反馈后仅目标阶段内容变化;阶段全部任务完成后该阶段进度徽章变为「已完成」且时间线节点变绿。
- 产出物:任务交互闭环。

#### 里程碑 M4:Resume Intelligence(任务 4.1 – 4.7)

**任务 4.1 简历数据模型与文件上传**

- 做什么:实现 Resume、ResumeVersion、Optimization 的 tRPC Router;文件上传经 Route Handler(大文件流式上传,框架必需端点;限制 PDF/Word 与大小上限),每次上传创建新 Resume 记录,原始文件永不覆盖。文件存储经**接口抽象**(上传/下载/删除):MVP 用本地文件系统实现,生产切换 Vercel Blob(任务 5.3,切换不改业务代码)。**隐私策略(经确认)**:文件加密存储、原文保留、用户可删——提供删除能力(tRPC mutation + 存储层清理),设置页(任务 1.8)接入「简历文件管理」删除入口,删除后服务端文件同步清理。
- 依赖:任务 1.3(Schema)。
- 验证:上传合法 PDF/Word 成功;超大小或错误类型被拒绝且提示明确;原始文件不可被覆盖(两次上传产生两条记录);删除文件后不可再下载且服务端存储同步清理;上传接口有鉴权与越权测试;存储实现可切换(业务代码不直接依赖具体存储实现)。
- 产出物:简历数据层 + 上传组件 + 文件删除能力。

**任务 4.2 文本解析**

- 做什么:用 pdf-parse 与 mammoth 提取上传文件的纯文本;解析失败时展示降级路径:手动粘贴/输入简历文本。(图片型 PDF 无文本层无法解析——Phase 1 不做图片 OCR,引导粘贴输入。)
- 依赖:任务 4.1(上传)。
- 验证:准备 3 份样例简历(至少 1 份中文 PDF、1 份 Word)上传,提取的文本与原文人工比对无乱码、无大段缺失;故意上传图片型 PDF(无文本层),系统引导粘贴输入而非报错。
- 产出物:解析服务。

**任务 4.3 简历解析 Agent + 核对修正 UI**

- 做什么:按 agent-design 2.3 节第一步:编写解析 Prompt,从简历文本提取结构化信息(基本信息、教育、技能、经历、项目,输出 Schema 固定);解析结果展示核对修正界面,用户逐项修正后保存。
- 依赖:任务 4.2(文本解析)。
- 验证:解析样例集:3 份样例简历的解析结果与人工标注一致(关键字段无缺失);核对修正某段经历后保存,重新读取的数据与修正一致;输出通过 schema 校验。
- 产出物:简历解析 Agent + Prompt + 核对修正 UI + 样例集。

**任务 4.4 简历改写 Agent**

- 做什么:按 agent-design 2.3 节第二步:编写改写 Prompt,基于核对后的内容 + 画像能力标签 + 目标方向,逐段输出(原文、改写文、改写理由),遵循「不改事实、只重建叙事」边界。
- 依赖:任务 4.3(核对后内容)、任务 2.1(画像数据)。
- 验证:改写样例集:无量化数据的经历改写后不含虚构数字(边界测试);核对修正某段经历后,该段的改写结果随之变化;输出通过 schema 校验。
- 产出物:简历改写 Agent + Prompt + 样例集。

**任务 4.5 修改对比视图**

- 做什么:按 DesignSystem「Resume Analysis Card」:每条修改一张对比卡(修改前灰色引用块 / 修改后绿底绿边 / 折叠的「为什么这样改」AI 解释块 / 接受与拒绝按钮);接受/拒绝可撤销;顶部工具条:全部接受、导出、重新分析。
- 依赖:任务 4.4(改写输出)。
- 验证:接受后该条进入最终文本,拒绝后恢复原文;全部接受/全部拒绝边界正常;刷新后接受/拒绝状态保留;逐条操作与 PRD FR-36 一致。
- 产出物:对比视图页。

**任务 4.6 ATS 评分**

- 做什么:对最终采纳后的简历生成 ATS 评分(百分制)+ 等级文字(≥80 优秀 / 60-79 良好 / <60 需改进)+ 改进建议列表;评分基于规则与 LLM 评估结合。
- 依赖:任务 4.5(对比视图的最终采纳文本)。
- 验证:同一份简历连续评分 2 次,分差 ≤10(稳定性);等级文字与分数区间严格对应;改进建议与简历实际缺陷相关(抽查)。
- 产出物:ATS 评估。

**任务 4.7 导出**

- 做什么:基础版:一键复制最终简历文本 + 导出 PDF(按采纳后的最终内容排版);后置增强:导出 Word。
- 依赖:任务 4.5(最终采纳文本)。
- 验证:导出的 PDF 打开后内容与「最终采纳文本」完全一致;空简历(全部拒绝)时导出按钮禁用且有提示。
- 产出物:导出功能。

#### 里程碑 M5:闭环整合(任务 5.1 – 5.3)

**任务 5.1 工作台 Dashboard**

- 做什么:按 DesignRules「Dashboard」规则实现:问候行(「本周完成 3 个任务,路线图进度 42%」式一句话)→ KPI 行(匹配度/路线图进度/简历版本/本周任务,大数字 + 增量徽章)→ Agent 顾问区(三个 Agent 卡含状态)→ 模块入口卡(最新进展 + 「继续上次」);全部组件四态齐全。

- 依赖:任务 5.1(工作台)、任务 2.5(画像)、任务 3.2(方向选择)、任务 4.3(简历解析)。
- 验证:按 PRD 5.3 节三条路径手工全链路走查,每步数据正确带出;首页未登录可见、已登录自动跳转;新用户从注册到看到画像概要全程 < 5 分钟(用秒表实测一次真实走查的耗时)。

### Phase 1 验收标准

- 对应的 PRD 指标具备记录能力:画像完成率、路线图开始执行率、优化接受率。

## Phase 2:增强能力

### Phase 2 目标

补齐求职闭环:用户粘贴目标 JD 即可获得匹配度分析与技能差距报告;画像数据开始产生复利(能力变化追踪、简历多版本)。

### Phase 2 功能

- **Job Matching**:JD 需求拆解(必备/加分/隐性)、能力映射、匹配度评分、逐项对比雷达图、投递建议
- **Skill Analysis(Coach)**:差距优先级排序、90 天周计划、学习资源推荐(免费优先)
- 画像能力变化追踪(版本对比);简历多版本管理(多目标方向)
- **登录与增长**:微信扫码登录(任务 6.7);分享卡片——画像/路线图生成图片(任务 6.8)
- **体验**:深色模式(任务 6.9,对齐 DesignSystem「Phase 2 规划」)

### Phase 2 明确不做 / 延后

除已排入本 Phase 的项(微信登录、分享卡片、深色模式)外,Phase 1「明确不做 / 延后」清单的其余各项(图片 OCR、初版简历、验证码注册、限流、移动端适配、JD 数据源自动接入、企业端接口)继续延后——不做即范围控制。

### Phase 2 开发任务

**任务 6.1 Matching Agent**

- 做什么:按 agent-design 2.4 节实现:JD 结构化拆解(显性要求 + 隐性要求 + 权重)→ 用户能力映射(直接/间接/可迁移匹配)→ 差距计算(达标/接近/不足)→ 策略建议。输入:JD 文本 + 画像数据(可选优化后简历)。
- 依赖:任务 1.6(Agent 基座)、任务 2.1(画像数据)。
- 验证:样例集:3 份手工标注的 JD,断言拆解出的要求与标注一致(必备/加分分类合理);匹配度在 0-100;边界测试:空 JD、纯英文 JD、无画像用户(降级为仅拆解不匹配)均不崩溃。
- 产出物:Matching Agent + Prompt + 样例集。

**任务 6.2 岗位匹配页**

- 做什么:JD 输入(粘贴)→ 匹配报告页:整体匹配度大数字、逐项对比列表(匹配项/部分匹配/差距)、用户 vs 岗位要求双线雷达图、隐性需求揭示、投递建议;支持「这个要求我其实满足」纠偏 → 补充信息 → 重新匹配。
- 依赖:任务 6.1(Matching Agent)、任务 1.7(布局)。
- 验证:报告各区块与 agent-design 2.4 输出一一对应;纠偏后重新匹配结果变化;无画像用户看到引导先完成画像;走查 DesignRules。
- 产出物:匹配报告页。

**任务 6.3 Coach Agent(技能分析)**

- 做什么:按 agent-design 2.5 节实现:差距优先级矩阵(重要性 × 差距大小)、90 天周计划(每周主题/任务/预估时长/产出要求/完成标准)、资源推荐(标注免费/付费,免费优先)。输入:目标岗位要求 + 画像能力基线 + 每周投入时间 + 学习偏好。
- 依赖:任务 1.6(Agent 基座)。
- 验证:样例集:输出通过 schema 校验;计划覆盖 90 天且每周任务数与每周投入时间匹配(时间预算一致性);差距排序与「重要性 × 差距」矩阵一致(抽查);资源推荐均标注免费/付费。
- 产出物:Coach Agent + Prompt + 样例集。

**任务 6.4 技能分析页**

- 做什么:差距优先级排序列表 → 90 天周计划时间线(与路线图组件复用视觉)→ 资源卡;页面与 Navigator 数据对齐(阶段目标作为差距分析的参照系)。
- 依赖:任务 6.3(Coach Agent)、任务 6.2(匹配报告页入口)。
- 验证:从匹配报告页可一键发起技能分析(数据自动带出);周计划渲染完整;走查 DesignRules 四态与自检清单。
- 产出物:技能分析页。

**任务 6.5 画像能力变化追踪**

- 做什么:画像更新时保留版本;结果页增加「历史对比」:当前 vs 上次的雷达图双线对比 + 能力变化列表(提升/下降徽章)。
- 依赖:任务 1.3(画像版本字段)、任务 2.7(画像更新)。
- 验证:两次不同画像数据对比渲染正确;只有一个版本时优雅降级(不显示对比入口);变化列表与两次数据差值一致。
- 产出物:画像版本对比。

**任务 6.6 简历多版本**

- 做什么:同一原始简历可生成多个目标方向的优化版本;版本列表 + 切换 + 复制为新版本。
- 依赖:任务 4.1(简历数据层)。
- 验证:两个版本独立接受/拒绝互不影响;切换后导出内容为对应版本;删除版本不影响原始简历。

**任务 6.7 微信登录**

- 做什么:接入微信开放平台扫码登录(应用注册、OAuth 流程);与现有账号的绑定/合并策略:同邮箱自动绑定,未绑定邮箱的微信用户引导设置邮箱+密码或绑定已有账号。

- 验证:微信扫码注册新账号、扫码登录已绑定账号;绑定冲突处理路径明确;现有邮箱+密码登录不受影响。
- 产出物:微信登录。
- **状态:2026-08-23 用户拍板本轮暂缓**(偏差记录)——接入微信开放平台扫码登录需先在微信开放平台完成应用注册并取得 AppID/AppSecret(当前无凭据,且 OAuth 回调域名须为已备案域名,开发期无法完整联调)。本轮零代码;待凭据就绪后按本节定义实现(绑定/合并策略与验证标准不变)。

- 做什么:画像与路线图生成分享图片(服务端渲染/截图),分享到微信等渠道;遵守设计约束(紫色仅用于 AI 内容标记;token 全引用)。

### Phase 2 验收标准

## Phase 3:高级AI能力

### Phase 3 目标

上线 Interview Agent 完成产品闭环的最后一块(从"我能去哪"到"我能过吗");Agent 之间开始真正的协作与数据智能。

### Phase 3 功能

- **Interview Agent**:基于简历 + 岗位 + 画像的个性化出题、对话式面试、逐题评估与综合报告
- **Multi-Agent 协作**:全局上下文统一、跨 Agent 数据联动(路线图项目 → 简历素材提示等)、冲突结论并列呈现与用户裁决
- 数据智能基础:个人成长报告、匿名聚合的路径有效性统计

### Phase 3 明确不做 / 延后

- 语音面试:确认不做(任务 7.2 为纯文字形态;PRD 十节原写「语音/文字」,偏差记录)。
- Phase 1/2「明确不做 / 延后」清单中仍延后的项(图片 OCR、JD 数据源自动接入、企业端接口、限流等)在本 Phase 仍不做。

### Phase 3 开发任务

**任务 7.1 Interview Agent 出题**

- 做什么:按 agent-design 2.6 节实现出题:输入简历 + 目标岗位 + 面试类型(行为面/技术面/案例面),输出 10-15 题(自我介绍/经历深挖/技术案例/情景假设/反问),每题附追问提示。
- 依赖:任务 1.6(Agent 基座)、任务 4.1(简历数据)、任务 6.1(岗位方向数据)。
- 验证:样例集:抽查 3 题均能从输入简历中找到出处(个性化而非通用题库);同一简历换岗位后题目差异明显;输出通过 schema 校验。
- 产出物:Interview Agent(出题)+ Prompt + 样例集。

**任务 7.2 面试对话界面**

- 做什么:这是全产品唯一允许对话形态的界面(DesignRules 特许,单独设计):面试官提问气泡 + 用户输入 + 逐题推进 + 追问 + 可选 STAR 结构提示;支持中断恢复与流式渲染。面试形态为**纯文字**(注:PRD 十节原写「语音/文字」,经确认 Phase 3 采用纯文字,偏差记录;语音不在规划)。
- 依赖:任务 7.1(出题)。
- 验证:完整跑一场 5 题短面试无卡顿;中断后重新进入可从断点继续;键盘操作完整;走查 DesignRules(此页之外不允许出现聊天式布局)。
- 产出物:模拟面试页。

**任务 7.3 回答评估与综合报告**

- 做什么:每题评估(内容评分 1-10、表达评分 1-10、改进建议);面试结束生成综合报告(总体评价、突出优势、主要短板、1-2 个重点改进方向——不罗列所有问题)。
- 依赖:任务 7.2(对话流程)。
- 验证:同一答案连续评估 2 次,分差 ≤2(稳定性);报告含优势/短板/重点改进三项;评估建议与回答内容相关(抽查)。
- 产出物:评估与报告。

**任务 8.1 全局上下文与跨 Agent 联动**

- 做什么:统一用户全局上下文(各 Agent 产出按版本写入,agent-design 4.3 节;版本/来源字段沿用任务 1.6 预留结构);实现联动规则:路线图完成的项目 → 简历页提示「可加入简历」;画像更新 → 提示路线图/简历可能需要重新生成;匹配结论与画像推荐冲突时按 agent-design 4.4 并列呈现双方依据,用户选择并记录。
- 依赖:任务 1.6(上下文版本/来源字段)、各模块 Agent 产出。
- 验证:联动提示在对应场景出现且同场景不重复骚扰;构造画像推荐与匹配结论冲突的样例,界面并列呈现两方依据,用户选择后该选择被记录;上下文版本错乱时不串数据(隔离测试)。
- 产出物:协作上下文层。

**任务 8.2 数据智能基础**

- 做什么:个人成长报告页(画像版本演进、任务完成趋势、匹配度变化曲线);匿名聚合统计(路径有效性:选择某方向用户的平均阶段达成率),仅使用脱敏数据。
- 依赖:任务 8.1(上下文)、任务 6.5(画像版本)。
- 验证:报告数据与数据库记录一致;聚合结果中不含任何个人信息;无足够数据时展示引导而非报错。
- 产出物:成长报告 + 聚合统计。

### Phase 3 验收标准

- 模拟面试全流程可用:个性化出题、对话推进、逐题评估、综合报告。
- 跨 Agent 联动规则生效,冲突呈现与用户裁决闭环可用。
- 成长报告与匿名统计正确;Phase 1/2 功能回归通过。
- 至此完成产品架构的六环价值闭环:自我认知 → 方向发现 → 路径规划 → 能力提升 → 价值表达 → 机会匹配。

## 全局原则(贯穿所有阶段)

1. **先跑通,再完善**:任何模块先做「最小可用」打通链路,标注「后置增强」的功能放后面;宁可功能少,不可链路断。
2. **每步可验证**:任务不含验证步骤就等于没做完;AI 输出一律用固定样例集回归。
3. **数据优先**:用户输入与原始数据(原简历、旧画像版本)永不丢失、永不被覆盖;删除操作需用户显式发起(设置页),删除后不可恢复。
4. **设计约束优先**:UI 任务以 DesignRules 自检清单为准绳,禁止事项即红线。
5. **小步提交**:每个任务结束即提交并更新 progress.md;一个任务失败不牵连其他任务。
