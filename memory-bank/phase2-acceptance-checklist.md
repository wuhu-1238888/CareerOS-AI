## 一、阶段 2 到底实现了什么(基于实际代码核验)

总览:阶段 2 实现了 **Career Profile(职业数字画像)模块的完整闭环**:四步采集表单 → AI 分析(进度可视化)→ 结构化画像结果页(概要/优势不足/六维雷达/推荐方向/发展建议)→「这不是我」纠偏重算 →「更新信息」主动更新 → Dashboard 问候行与过期提示。每次分析生成**不可变的新版本**,历史版本可查看。API/数据库/Agent 全部真实落地(非前端假数据)。

### 2.1 画像数据与 API

- **实现了什么**:CareerProfile / CareerPath 的完整数据层 + 版本模型(schema 已含 version/parentVersion)。两处阶段 1 schema 微调:`CareerPath.matchScore` Float 0~1 → **Int 0-100**;`AgentRun` 新增 `progress Json?` 列。tRPC `profile` 命名空间:get(最新版+方向,按匹配度降序)/ listVersions / getVersion / create / update / delete + `careerPath.{list,create,delete}`。全部接口要求登录且只能访问自己的数据(越权一律「画像不存在」);数据库 JSON 列读取前经 zod 校验,损坏回退空值。
- **用户可以做什么**:无直接 UI(数据层)。它决定用户每次分析的数据如何保存、如何读取、如何隔离。
- **涉及页面**:无独立页面。
- **核心交互**:无直接交互。
- **是否涉及 AI**:否。
- **是否涉及 API/数据库**:是。API = tRPC profile 命名空间(8 个端点);DB = CareerProfile/CareerPath/AgentRun.progress。
- **与其他任务的关系**:2.2/2.4/2.5/2.6/2.7 的读写基础;版本字段是 2.6/2.7「新版本+旧版本可查看」的前提。

### 2.2 分步采集表单

- **实现了什么**:四步表单(教育背景 → 技能 → 经历 → 兴趣与目标),每步顶部一句「为什么需要」。必填仅学历+专业+技能;经历与目标可跳过。技能 = 30 项预设 chips + 自由输入 + ●○○/●●○/●●● 三级熟练度(上限 20);学历 5 档下拉、毕业年份下拉(1980–2035);经历 = 实习/项目结构化条目(公司/职位/内容,上限 10);兴趣 10 预设多选;目标自由输入(上限 5)。失焦校验 + 步进拦截提示。草稿随输入写入 localStorage(`careeros:profile-draft:{userId}`),刷新不丢,提交成功才清除。
- **用户可以做什么**:首次填写或更新自己的背景信息,中途刷新不丢,提交触发 AI 分析。
- **涉及页面**:/profile(无画像/更新信息/修改信息三种入口共用)。
- **核心交互**:步进器(完成=绿✓、当前=黑、未来=灰)、底部固定「上一步/下一步/生成我的画像」、chips 多选、三级熟练度切换、草稿保存恢复。
- **是否涉及 AI**:否(提交后由 2.4 管线进入 AI)。
- **是否涉及 API/数据库**:提交走 profile.analyze(2.4);草稿仅 localStorage,不落库。
- **与其他任务的关系**:2.4 的输入源;2.7 复用它做「更新画像」预填。

### 2.3 Profile Agent

- **实现了什么**:`career-profile-analyzer` Agent(注册到意图 analyze-profile)+ 独立 Prompt 文件 `profile-analyst.md`。Prompt 严格按 agent-design 2.1:角色锚定 / 五步推理(信息完整性→能力分级→方向匹配→差距分析→叙事生成)/ 六维雷达(产品/技术/数据/沟通/项目/行业)/ 边界限制(不编造能力、不做确定性判断、不替用户决策、不给无依据评分)/ 不确定性表达(置信度 高/中/低)/ 纠偏反馈处理段。输出 Schema:summary / abilityTags 3-10(基础/熟练/精通)/ strengths 3-5 / directions 2-4(匹配度 0-100+理由+优劣势)/ 六维雷达 0-100 / suggestions 1-5 / confidence。固定样例集 3 份(信息齐全/部分缺失/仅必填)+ 手工标注。
- **用户可以做什么**:不可见。用户感知 = AI 分析的质量与可信度。
- **涉及页面**:无(输出由 2.5 结果页渲染)。
- **核心交互**:无。
- **是否涉及 AI**:是(核心 AI)。LLM 经适配层调用,当前环境为 mock,生产切 DeepSeek。
- **是否涉及 API/数据库**:间接(输出经 2.4 管线落库;AgentRun 记录每次调用)。
- **与其他任务的关系**:2.4 的执行体;输出结构是 2.5 结果页的渲染契约;feedback 字段服务 2.6。

### 2.4 分析管线与过程页

- **实现了什么**:`analyzeProfile` 管线:创建 AgentRun(running)→ Orchestrator 执行 Profile Agent,5 个生命周期进度事件**实时写入 AgentRun.progress**(串行化防丢失)→ 成功:创建**新版本行**(version=max+1,parentVersion=上一版本号)+ 推荐方向全量重建;失败:友好错误 + AgentRun failed,**不创建新行**。tRPC:`profile.analyze`(等待执行完成)/ `profile.retry`(从 AgentRun.input 服务端重放)/ `profile.getRun` / `profile.latestRun`。**stale 判据**:running 且超过 2 分钟未更新 → 序列化为失败「分析中断,请重试」。过程页 = Agent 卡(画像顾问 + AI 徽章 + 「分析中」badge + spinner)+ 4px 进度条(按 5 事件推进)+ 文案轮播(「正在理解你的背景与目标…」等);页面轮询 latestRun 700ms;刷新页面按最近 run 恢复;失败视图「重试/修改信息」。
- **用户可以做什么**:提交后观看分析进度;分析中刷新不丢;失败后一键重试或返回修改;会话内失败重试用最近一次提交的数据(含纠偏反馈),刷新后重试由服务端重放。
- **涉及页面**:/profile(分析过程视图)。
- **核心交互**:进度条+文案轮播、重试、修改信息、刷新恢复。
- **是否涉及 AI**:是(调度执行)。
- **是否涉及 API/数据库**:是。API = analyze/retry/getRun/latestRun;DB = AgentRun(status/progress/input/output)+ CareerProfile 新版本行 + CareerPath。
- **与其他任务的关系**:2.2+2.3 的接线点;2.6/2.7 复用同一管线产生新版本;过程页模式是 3.4 的复用对象。

### 2.5 画像结果页

- **实现了什么**:渲染前对 aiAnalysis 做 zod 校验(非法 →「分析数据异常,请重新分析画像」)。区块顺序:概要卡(摘要 + 能力标签分级色 + 置信度 badge + 说明)→ 优势/不足双列(优势 ✓ 绿、可展开 AI 详情;不足 ✗ 红、来自方向差距并标注来源方向)→ 六维雷达(Recharts,chart-green 20% 填充 + HTML 图例)→ 推荐方向卡 2-4 张(32px 大数字匹配度 + 理由 + 优劣势)→ 发展建议编号列表。**版本选择器**(>1 版本时出现,可查看任意历史版本)。页面头动作:「更新信息」ghost /「优化简历」ghost(→/resume)/「这不是我」ghost /「规划成长路线」primary(→/navigator)。
- **用户可以做什么**:查看完整画像、切换历史版本、发起纠偏/更新、跳转下游模块。
- **涉及页面**:/profile(结果视图)。
- **核心交互**:优势条目展开/收起、版本下拉切换、4 个页面头动作按钮。
- **是否涉及 AI**:展示 AI 输出(所有区块带 ai-badge 紫标)。
- **是否涉及 API/数据库**:读 profile.get / listVersions / getVersion。
- **与其他任务的关系**:2.3 输出的渲染;2.6 纠偏入口(这不是我);2.7 更新入口(更新信息);「规划成长路线/优化简历」是 3.x/4.x 的入口。

### 2.6 纠偏流程

- **实现了什么**:「这不是我」→ 弹窗(三组 checkbox:推荐方向不准确/能力评估不准确/优势判断不准确 + 补充说明 ≤500 字)→ 提交 → 关闭弹窗 → Toast「已记录,AI 将重新分析」→ **带 feedback 全量重算**(同一管线)→ 新版本,旧版本仍可查看。重算期间展示分析过程视图(优先级高于旧结果);重算失败 → 失败视图,重试**携带反馈**(会话内重放/刷新后服务端重放)。
- **用户可以做什么**:指出分析不准确的部分并补充说明,让 AI 重新分析;随时查看旧版本。
- **涉及页面**:/profile(结果视图 + 纠偏弹窗)。
- **核心交互**:弹窗多选、补充说明、Toast 确认、重算进度、版本递增。
- **是否涉及 AI**:是(feedback 注入 Agent 输入重算)。
- **是否涉及 API/数据库**:profile.analyze(feedback)/ retry;新版本行 + 旧版本保留。
- **与其他任务的关系**:依赖 2.4 管线 + 2.5 入口 + 1.3 版本字段;反馈闭环对应 agent-design 3.4「这不是我」。

### 2.7 画像主动更新 + Dashboard 提示

- **实现了什么**:结果页「更新信息」→ 复用 2.2 表单并预填最新版本数据(标题「更新画像信息」)→ 提交走同一管线 → 新版本号递增。Dashboard(/dashboard)接入问候卡:问候行「你好,{昵称}」+ 画像状态行(「画像 v2 · 已更新于 X」/ 无画像 →「去创建」引导);最新画像 createdAt **超过 7 天** → 琥珀色提示条「画像信息已超过 7 天,建议更新以获得更准确的建议」+「更新画像」链接。
- **用户可以做什么**:回访时更新画像(新增技能/经历后重算);Dashboard 一眼看到画像是否过时。
- **涉及页面**:/profile(更新表单)、/dashboard(问候卡)。
- **核心交互**:预填表单编辑、版本递增、7 天过期提示。
- **是否涉及 AI**:是(复用分析管线)。
- **是否涉及 API/数据库**:profile.get / user.me;新版本行。
- **与其他任务的关系**:覆盖 PRD FR-14 + PRD 5.2 回访流程;完整工作台(KPI 行/Agent 区/模块入口)属任务 5.1,不在本阶段。

## 三、具体验收步骤(可照做)

> 前提:准备两个测试账号(可用邮箱临时注册)。步骤中用「账号甲」走主流程。
> 若已配置 DeepSeek Key:全步骤适用;若仍为 mock:步骤 H(失败分支)适用,H 之后的「成功结果」类步骤会走到失败分支,属环境限制而非产品缺陷(见验收前须知)。

### 步骤 S1:首次创建画像(对应 A1)

1. 打开 http://localhost:3000,用账号甲登录
2. 点击顶栏「职业画像」进入 /profile
3. **步骤 1 教育背景**:学历选「本科」;专业输入「计算机科学与技术」;学校(选填)输入「示例大学」;毕业年份(选填)选「2026」→ 点「下一步」
4. **步骤 2 技能**:点击预设 chip「Python」「SQL」(chip 变绿 ✓);在「添加其他技能」输入「Go」回车 → 已选列表出现 Go(默认熟练);把 Go 的熟练度切到「●○○ 基础」;再切回 → 点「下一步」
5. **步骤 3 经历**:点「添加实习经历」→ 公司「示例科技」/ 职位「后端实习生」/ 内容「参与内部数据平台接口开发与联调」;点「添加项目经历」→ 名称「校园二手交易平台」/ 角色「后端开发」/ 描述「独立完成订单模块的设计与开发」→ 点「下一步」
6. **步骤 4 兴趣与目标**:点选兴趣 chip「后端开发」「人工智能」;目标输入「后端开发工程师」→ 点「添加」→ 底部按钮显示「生成我的画像」→ 点击
7. 观察分析过程页(配置了真实 Key):进度条 0→100%、文案从「正在理解你的背景与目标…」→「正在分析…」→「正在整理分析结果…」→「分析完成」逐条出现、已完成项带绿色 ✓、当前项带 spinner
8. 自动进入结果页

**预期结果**:结果页自上而下出现 概要卡(2-3 句摘要 + 能力标签带分级 + 置信度 badge)→ 优势/不足双列(✓ 绿 / ✗ 红)→ 六维雷达(六个维度有连线图 + 下方图例数值)→ 推荐方向卡 2-4 张(每张 32px 绿色大数字匹配度 + 理由 + 优劣势)→ 发展建议编号列表;顶部有「更新信息/优化简历/这不是我/规划成长路线」四个按钮;所有 AI 区块有紫色 AI 徽章。

### 步骤 S2:结果页交互(对应 A1/B3/B5)

1. 接 S1,点优势列任一条目 → 展开一行 AI 详情,再点收起
2. 点「规划成长路线」→ 跳转 /navigator(占位页「模块建设中」属 M3,此时正常);点「优化简历」→ 跳转 /resume(同理)
3. 返回 /profile,结果仍在(数据已落库)
4. 刷新页面 → 直接显示结果页(不再显示表单)

**预期结果**:展开/收起正常;跳转正确;刷新后结果不丢。

### 步骤 S3:纠偏闭环(对应 A2)

1. 接 S2,点「这不是我」→ 弹窗出现,标题「哪些部分不准确?」
2. 直接点「提交反馈」→ 弹窗内出现「请选择不准确的部分」且弹窗不关闭
3. 勾选「推荐方向不准确」,补充说明输入「我更想做产品方向,而不是后端」→ 点「提交反馈」
4. 弹窗关闭 → 顶部 Toast「已记录,AI 将重新分析」→ 进入分析过程视图(不是旧结果)
5. 等待完成 → 新结果页出现
6. 看版本选择器:下拉中应有「v2 · 今天」「v1 · 今天」两个版本
7. 切到 v1 → 显示旧版内容(旧摘要/旧方向还在);切回 v2 → 新内容
8. 再次点「这不是我」重做一次纠偏 → 出现 v3

**预期结果**:空提交被拦截;反馈后重算;**新版本内容回应了反馈**(如方向里出现产品相关方向或 confidence.note 提到反馈);版本号递增、旧版本内容不变;纠偏入口可多次使用。

### 步骤 S4:更新信息 + Dashboard 提示(对应 A3/A4)

1. 接 S3,点「更新信息」→ 出现标题「更新画像信息」的表单,专业已预填「计算机科学与技术」、技能已预填 Python/SQL/Go
2. 把专业改成「数据科学」,技能加一个「数据分析」→ 一路「下一步」→「生成我的画像」→ 新版本 v4
3. 点顶栏「工作台」进入 /dashboard
4. 用「时间>7 天」的账号验证提示:用另一个账号(账号乙)完成一次画像;用数据库工具把该账号最新画像行的 created_at 改为 8 天前(或等自然时间,验收时可请求开发协助改时间)→ 登录账号乙 → 工作台

**预期结果**:更新后版本号递增;Dashboard 账号甲:问候「你好,{昵称}」+「画像 v4 · 已更新于 …」、无过期提示;账号乙:问候 + 「画像 v1 · 已更新于 …」+ 琥珀色提示「画像信息已超过 7 天,建议更新以获得更准确的建议」+「更新画像」链接指向 /profile。

### 步骤 S5:草稿与必填校验(对应 A5)

1. 用账号乙登录 → /profile → 步骤 1 什么都不填,点「下一步」→ 停在步骤 1,「请选择学历」「请输入专业」红字提示
2. 填学历+专业 → 下一步 → 步骤 2 一个技能都不选点「下一步」→ 红字「请至少添加一项技能」
3. 选一个技能 → 下一步 → 步骤 3/4 直接「下一步」(可跳过)→ 底部出现「生成我的画像」,**不要点**
4. 刷新页面 → 仍停在步骤 4,之前填的所有内容都在(草稿恢复)
5. 回退到步骤 1 改专业 → 再次刷新 → 修改后的专业也在

**预期结果**:必填拦截与提示具体;选填步骤可跳过;刷新后草稿完整恢复。

### 步骤 S6:分析失败与重试(对应 A6;mock 环境即可做)

1. 账号乙(mock 环境)提交「生成我的画像」→ 进入分析过程,随后出现红色失败面板:「AI 返回了无法识别的结果,请稍后重试」(若配置了真实 Key,此步改用「拔网线/停服务」制造失败,或跳过)
2. 点「修改信息」→ 回到表单,之前填写的内容仍在(草稿未清)
3. 再次提交制造一次失败 → 点「重试」→ 再次进入分析过程(重新提交了同一份数据)
4. 失败后刷新页面 → 仍显示失败视图(可重试/修改信息),而不是回到空表单

**预期结果**:错误文案友好、无裸堆栈;修改信息不丢草稿;重试可用;刷新后失败态可恢复。

### 步骤 S7:分析中刷新恢复 + 中断判失败(对应 A7;需真实 Key)

1. 配置真实 Key 后提交分析,在进度条未到 100% 时刷新页面 → 应回到分析过程视图并从已落库的进度继续
2. 中断复现:提交后立刻杀掉 dev server(Ctrl+C)→ 等 2 分钟以上 → 重启 → 进入 /profile → 显示「分析中断,请重试」+ 重试按钮 → 点「重试」→ 成功进入结果页

**预期结果**:刷新不丢任务;中断超 2 分钟判定失败并可重试恢复。

### 步骤 S8:数据真实性抽查(对应 A8)

1. 完成 S1–S4 后,用 psql 查库(开发协助):`SELECT id, version, parent_version FROM "CareerProfile" WHERE user_id = '{甲}' ORDER BY version;` → 应有 v1..v4,parent_version 依次为 null/1/2/3
2. `SELECT intent, status, jsonb_array_length(COALESCE(progress,'[]'::jsonb)) FROM "AgentRun" WHERE user_id='{甲}' AND intent='analyze-profile';` → 成功 run status=succeeded、progress 长度 5;失败 run status=failed
3. CareerPath 只属于最新版本行,匹配度 0-100 整数
4. 浏览器退出账号甲,登录账号乙 → /profile 看不到甲的任何数据;甲也看不到乙的

**预期结果**:版本链完整;AgentRun 有痕迹;数据隔离。

## 四、正常流程验收(Happy Path)

从一个全新用户视角的完整闭环(建议按此顺序一次走完,≈10-15 分钟;PRD 要求首次到画像概要 <5 分钟,可计时步骤 2-6):

1. **开始**:浏览器打开 http://localhost:3000 → 注册新账号(邮箱+昵称+密码,≥8 位)→ 自动登录
2. **进入**:顶栏点「职业画像」
3. **填写**:按 S1 步骤 3-6 走完四步(教育→技能→经历→目标)
4. **分析**:点「生成我的画像」→ 看到「画像顾问」Agent 卡 + 进度条 + 文案轮播
5. **结果**:自动进入结果页 → 从上到下依次看到 概要/优势不足/雷达/方向卡/发展建议,匹配度是大数字 32px
6. **纠偏**:点「这不是我」→ 勾选不准确项 → 提交 → Toast → 重算 → v2,版本下拉可切回 v1
7. **更新**:点「更新信息」→ 预填表单改一项 → 提交 → v3
8. **回访**:点顶栏「工作台」→ 看到「你好,{昵称}」+「画像 v3 · 已更新于 …」;若画像 >7 天,还看到建议更新提示条 → 点「更新画像」回到 /profile
9. **终点**:用户拥有 v1-v3 完整版本链的画像;下一步(规划成长路线/优化简历)入口就绪(跳转到 M3/M4 占位页)

每一步「应该看到什么」见第三部分对应步骤的预期结果。

## 六、AI 功能验收(单独清单)

> 前提:除「失败反馈」外,本节需要配置真实 DeepSeek Key 才能做;mock 环境下 AI 必然输出失败(见验收前须知)。管线正确性已被 167 项工程测试与固定样例集覆盖,但**真实 LLM 的输出质量只能本节验证**。

### 6.1 十项检查

| # | 检查点 | 怎么验 | 判据 |
|---|---|---|---|
| 1 | AI 是否真的使用了用户输入? | 用「文科转运营」资料提交(S1 改专业为新闻传播、技能为内容运营/文案写作/PPT) | 结果中的能力标签、方向必须与输入相关(如出现「新媒体运营」),不得出现输入里没有的专业能力(如不会凭空出现「C++」) |
| 2 | 输出与输入是否相关? | 对比输入与摘要/方向/雷达 | 摘要提到的背景能在表单数据里找到出处 |
| 3 | 是否符合产品定位? | 通读摘要与建议语气 | 建议口气(「你可能适合…」),无「你一定适合」;无替用户决策 |
| 4 | 是否有实际价值? | 看方向理由与差距建议 | 每个方向有可解释的理由;建议是具体行动而非空话 |
| 5 | 是否稳定? | 同一份数据连续生成 2 次 | 方向集合与匹配度大致一致(允许小幅波动);不会一次 85 一次 10 |
| 6 | 是否明显幻觉? | 故意只填必填(学历+专业+1 技能) | 不得出现未提供的实习/项目/技能;置信度为「低」并有保守说明 |
| 7 | 输出格式是否正确? | 结果页能否完整渲染 | 各区块齐全;匹配度是 0-100 整数;雷达 6 维 0-100;无「分析数据异常」报错 |
| 8 | Loading 状态是否合理? | 提交后观察 | 进度条+文案轮播逐条出现;无空白等待;完成后自动进入结果 |
| 9 | 失败反馈是否明确? | mock 环境提交 | 「AI 返回了无法识别的结果,请稍后重试」+ 重试/修改信息 |
| 10 | 是否只是固定模板? | 两个完全不同背景的账号分别生成 | 结果必须随输入变化。**说明**:当前 mock 环境连模板都算不上(必然失败,不会假装成功);进度文案(5 条生命周期文案)是 1.6 的确定性设计,非 LLM 生成——这属产品设计决策,不视为「假 AI」。真实 Key 下输出完全来自模型 |

### 6.2 具体测试案例(3 个,需真实 Key)

**案例 A:信息齐全的计算机应届生**(与工程样例集 cs-grad 同源)

输入:S1 的完整数据(计算机本科 2026 / Python 熟练、SQL 熟练、JavaScript 基础 / 后端实习+校园平台项目 / 兴趣后端+AI / 目标后端开发工程师)

预期 AI 输出:置信度「高」;方向含「后端开发」且匹配度较高(示例标注 85);雷达「技术」维显著高于「产品/沟通」;不足处提到类似「缺少高并发/分布式经验」;建议是具体项目行动。

重点检查:方向与目标一致;每个分数能在输入中找到依据;摘要不超过 3 句、无夸张。

**案例 B:文科背景转运营**(与样例集 liberal-to-ops 同源)

输入:新闻传播本科 / 内容运营熟练、文案写作熟练、PPT 熟练 / 项目经历=校园公众号主编 / 兴趣=运营 / 无目标

预期 AI 输出:置信度「中」;方向含「新媒体运营」「内容策划」一类运营岗,不应推荐「后端开发」;雷达「沟通」维偏高、「技术」维偏低。

重点检查:不编造未提供的技术能力;无目标时方向推荐来自兴趣与能力,且说明理由;置信度降为「中」并解释缺了什么。

**案例 C:仅必填的最小输入**(与样例集 minimal 同源)

输入:电子商务本科 / 仅「数据分析(基础)」一项技能 / 无经历无目标

预期 AI 输出:置信度「低」;方向保守(匹配度不高,示例标注 45/40);雷达各维分数低;摘要与建议提示「补充信息后更新画像」;优势数量取最小值 3。

重点检查:不崩溃;不编造经历与能力;低置信度有说明;建议引导用户补充信息(符合 PRD「先粗略填写→后续完善」)。

| 禁止项抽查 | 无聊天式界面;无「精准预测/100% 匹配」话术;无裸 JSON/字段名/堆栈;无虚假精确度(匹配度只到个位+置信度 badge+note) |

## 十一、什么时候算「阶段 2 通过」

结合 CareerOS 阶段 2 的实际情况,通过标准为:

1. **P0 全部通过**。其中 P0-1/P0-10/P0-11/P0-12 依赖真实 DeepSeek Key;若你决定本次不配置 Key,则 P0-10/P0-11(真实 LLM 质量)可降级为「遗留验证项」,**其余 P0 必须全部通过**(失败分支、纠偏、更新、Dashboard、数据链、隔离在 mock 下均可验证,管线正确性另有 176 项工程测试背书)。
2. **P1 无阻塞性问题**:允许个别 P1 未过但须记录;P1-3/P1-7 若因环境无法复现,不视为阻塞。
3. **无严重数据错误**:版本链完整、无数据丢失/重复/串号(全局原则 3)。
4. **核心 AI 链路未失效**:AI 调用→结构化校验→落库→渲染→纠偏重算的链路完整;AI 失败时有明确反馈与恢复路径(FR-42)。
5. **核心用户流程完整走通**:新用户从表单到画像结果(或明确的失败反馈)全程无裸错误、无白屏、无英文堆栈。
6. **不要求**:路线图/简历功能(属 M3/M4)、分享卡片与微信登录(Phase 2 延后清单)、真实 LLM 稳定性指标(需多次真实调用积累)。

满足以上即阶段 2 通过,可进入 M3(任务 3.1 起)。

## 附录:发现但未修改的问题(本次只发现,不修复)

> 按影响排序。**#1 是阻塞性环境问题**,直接影响浏览器端 Happy Path 验收。

1. **【阻塞·环境】当前 `.env` 为 `LLM_PROVIDER="mock"` 且无真实 Key,默认 Mock 回复(回显用户消息)无法通过 Profile Agent 输出校验 → 浏览器端「生成我的画像」必然失败**。这不是产品缺陷而是配置未就绪:管线在测试中以注入式 Mock(手工构造合法 JSON)证明正确,但应用默认 mock 没有合法画像输出。验收 Happy Path 前需在 `.env` 配置 `LLM_PROVIDER="deepseek"` + `DEEPSEEK_API_KEY`(纯配置,不改代码)。也正因如此,「AI 假装成功输出固定模板」的问题不存在——mock 下宁可失败也不伪造成功。
2. **【PRD 偏差·P2】经历缺少「时长」字段 —— 已于 2026-08-20 修复**:PRD 3.1.3 实习/工作经历要求「公司、岗位、时长、主要职责」,原实现无时长字段。修复:`experienceEntrySchema` 增加 startDate/endDate(YYYY-MM,endDate=null 表示「至今」)与 duration;`computeExperienceDuration` 由系统自动计算「X年Y个月」,至今时按当前月份计算并标注「 · 至今」,用户不手动填写。表单经历卡增加开始/结束月份输入 +「至今」checkbox(勾选后结束时间禁用)+ 实时「时长:X」展示 + 逐条校验(请选择开始时间/请选择结束时间或勾选「至今」/结束时间不能早于开始时间)。时长随经历落库并经管线进入 Agent 输入,profile-analyst.md 提示 AI 用时长度量经验深度与稳定性、不得据此编造细节。仅实习/工作经历含时长(项目经历按 PRD 保持名称/角色/成果);JSON 列无迁移,旧数据兼容。
3. **【设计偏差·P2】Toast 位置 —— 已于 2026-08-20 修复**:DesignSystem 规格「右下 Toast」,sonner 配置为 top-center。修复:根布局 `<Toaster position="bottom-right" />`,一处配置改动。
